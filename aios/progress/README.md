# AIOS Progress System

This folder is the runtime record of task execution. It is the operational counterpart to the
master spec (`docs/AIOS_Master_Task_Specification_M0-M26.md`).

## Layout
```text
aios/progress/
├── PLAN.md              # entry point (points to docs/PLAN.md)
├── README.md            # this file
├── LOG.md               # append-only session/progress log
├── STATS.md             # live metrics
├── task-registry.json   # GENERATED by parse_spec.py (Rule 1 / Rule 2)
├── task-index.md        # GENERATED human index (Rule 2)
└── tasks/
    ├── _TEMPLATE/       # copy this for each new task
    └── TASK-xxx/        # one folder per task
```

## Rules
- One folder per TASK-ID. IDs come from the master spec and are **immutable** (Rule 1).
- To add a task: edit the master spec (add a `## TASK-xxx` entry under the right `# Mx`
  header), then re-run `parse_spec.py`.
- Never hand-number a task ID. Never reuse a number.
- A task is CLOSED only when `python ../scripts/gate_check.py TASK-xxx` passes (Rule 6).

## The enforcement engine lives in `aios/governance/`
Each General Rule is a real, tested Python module (not a convention):
- Rule 1 `task_registry` · Rule 2 `dependency` · Rule 3 `architecture`
- Rule 4 `deterministic` · Rule 5 `evidence` · Rule 6 `lifecycle` · Rule 7 `regression`
- Unified decision: `gates.gate.TaskGate`

All modules have automated pytest tests under `aios/governance/<component>/tests/`.

## Regenerating the registry
```text
python aios/scripts/parse_spec.py
```
Validates unique IDs (Rule 1) and derives each task's milestone from the `# Mx` headers
in the master spec (Rule 2), then writes `task-registry.json` + `task-index.md`.
