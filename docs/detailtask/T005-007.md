# TASK-005 — Runtime Services II

## 1. Mục tiêu

Hoàn thiện phần còn lại của **Runtime Kernel** để AIOS có thể thực sự quản lý vòng đời một execution thay vì chỉ cung cấp các primitive/service độc lập.

TASK-005 tập trung vào bốn năng lực runtime quan trọng:

1. **Execution** — thực thi workflow/execution plan.
2. **Scheduler** — điều phối thời điểm chạy và technical queue.
3. **State** — quản lý trạng thái execution, checkpoint và snapshot/resume.
4. **Resource** — quyết định execution có thể chạy dựa trên tài nguyên hiện có.

Sau TASK-005, các service phải được composition thành một **RuntimeKernel** thống nhất nhưng vẫn giữ nguyên nguyên tắc service độc lập, contract-first và dependency injection.

Runtime phải đảm bảo chuỗi:

```text
Execution Request
      ↓
Policy Pre-check
      ↓
Resource Check
      ↓
Scheduler
      ↓
Execution Service
      ↓
State / Checkpoint
      ↓
Artifact / Event / Audit
```

Execution không được tự ý bỏ qua Policy, Permission hoặc Resource Service.

---

## 2. Phạm vi

### 2.1 Execution Service

Triển khai service chịu trách nhiệm thực thi execution plan/workflow.

Các capability tối thiểu:

* nhận `ExecutionPlan`;
* tạo execution instance;
* tạo execution context;
* chuyển execution qua state machine;
* thực thi node theo thứ tự;
* hỗ trợ retry;
* timeout;
* cancellation;
* failure propagation;
* checkpoint tại node boundary;
* snapshot;
* resume;
* phát event trong suốt lifecycle.

Execution Service **không tự quyết định policy**.

Trước khi execution bắt đầu phải có policy decision hợp lệ.

---

### 2.2 Retry

Retry phải là behavior có kiểm soát, không phải vòng lặp vô hạn.

Execution cần hỗ trợ:

```yaml
retry:
  max_attempts: 3
  backoff: exponential
  retryable_errors:
    - timeout
    - transient_failure
```

Mỗi attempt phải được ghi nhận:

```text
execution_id
node_id
attempt
started_at
finished_at
status
error
```

Retry không được làm mất evidence của attempt trước.

---

### 2.3 Timeout

Mỗi execution/node có thể có timeout.

Khi timeout:

```text
RUNNING
   ↓
TIMEOUT
   ↓
Retry / Fail / Recovery
```

Timeout phải:

* deterministic;
* observable;
* audit được;
* không để execution tiếp tục chạy ngầm sau khi đã bị terminate/cancel.

---

### 2.4 Cancellation

Execution phải hỗ trợ:

* cancel pending execution;
* cancel running execution;
* propagate cancellation tới node đang chạy;
* lưu trạng thái cuối;
* phát cancellation event.

Cancellation không được làm hỏng snapshot hoặc artifact đã được tạo trước đó.

---

### 2.5 Scheduler Service

Scheduler ở TASK-005 là **technical scheduler**, không phải Orchestrator Task Queue.

Phân biệt:

```text
Task Queue
→ logic orchestration
→ "task nào cần làm?"

Scheduler Service
→ technical scheduling
→ "khi nào execution được chạy?"
```

Scheduler tối thiểu hỗ trợ:

* one-shot execution;
* queued execution;
* scheduled execution;
* priority;
* pause/resume;
* cancellation;
* execution dispatch.

Scheduler không sở hữu Resource implementation.

---

### 2.6 State Service

State Service quản lý state machine của execution.

Tối thiểu:

```text
CREATED
PENDING
READY
RUNNING
SUCCEEDED
FAILED
CANCELLED
TIMEOUT
```

State transition phải được kiểm soát, không cho phép transition tùy ý.

Ví dụ:

```text
CREATED → PENDING → READY → RUNNING → SUCCEEDED
                              ↓
                            FAILED
                              ↓
                            RETRY
```

Mỗi transition phải có event/evidence tương ứng.

---

### 2.7 Checkpoint

Checkpoint được tạo tại boundary phù hợp, tối thiểu sau khi một node hoàn thành.

Checkpoint cần lưu reference tới:

* execution state;
* context;
* completed nodes;
* pending nodes;
* artifact references;
* execution metadata.

Không nhất thiết copy toàn bộ artifact vào checkpoint; có thể lưu immutable reference/hash.

---

### 2.8 Snapshot / Resume

Snapshot là artifact đại diện cho execution state tại một thời điểm.

Resume phải cho phép:

```text
Execution
   ↓
Checkpoint
   ↓
Snapshot
   ↓
Process restart / failure
   ↓
Load snapshot
   ↓
Validate
   ↓
Resume
```

Resume phải kiểm tra:

* snapshot integrity;
* workflow/version compatibility;
* execution state;
* artifact references;
* policy validity;
* resource availability.

Không được resume một snapshot invalid hoặc corrupted.

---

### 2.9 Resource Service

Resource Service quản lý tài nguyên runtime.

Tối thiểu:

```text
CPU
RAM
GPU
Disk
Token Budget
Concurrent Workflows
Docker Containers
```

Resource decision:

```text
REQUEST
  ↓
Resource available?
 ├── YES → GRANT
 ├── NO + queueable → QUEUE
 └── NO + non-queueable → REJECT
```

Resource Service chỉ quyết định resource allocation.

Nó không thực thi workflow và không thay thế Scheduler.

---

### 2.10 RuntimeKernel

RuntimeKernel là composition root của các runtime service.

Ví dụ:

```text
RuntimeKernel
├── ExecutionService
├── ContextService
├── EventService
├── ArtifactService
├── PermissionService
├── PolicyService
├── SchedulerService
├── StateService
└── ResourceService
```

Kernel chịu trách nhiệm:

* wiring dependency;
* lifecycle;
* startup;
* shutdown;
* health;
* service resolution.

Kernel **không trở thành God Object**.

Logic nghiệp vụ vẫn nằm trong từng service.

## 4. Acceptance Criteria

### AC-005-01 — Execution

Một execution plan hợp lệ có thể được thực thi từ đầu đến cuối và trả về execution result có cấu trúc.

### AC-005-02 — Policy Enforcement

Execution bị từ chối nếu Policy Service trả về `DENY`.

Không được có execution path bypass Policy.

### AC-005-03 — Retry

Transient failure được retry đúng số lần cấu hình.

Retry vượt `max_attempts` phải kết thúc bằng failure có evidence.

### AC-005-04 — Timeout

Execution/node vượt timeout phải chuyển sang trạng thái timeout hoặc recovery state hợp lệ và không tiếp tục chạy ngầm.

### AC-005-05 — Cancellation

Running execution có thể được cancel và state cuối phản ánh cancellation.

### AC-005-06 — Checkpoint

Execution tạo checkpoint tại execution boundary đã định nghĩa.

Checkpoint phải truy được execution state và artifact references.

### AC-005-07 — Resume

Execution có snapshot hợp lệ có thể resume sau restart/failure mà không chạy lại các node đã hoàn thành ngoài policy retry.

### AC-005-08 — Resource

Resource request phải trả về đúng một trong:

```text
GRANT
QUEUE
REJECT
```

theo resource availability và policy.

### AC-005-09 — Scheduler Separation

Scheduler không trực tiếp quản lý resource allocation hoặc execution implementation.

### AC-005-10 — Kernel

RuntimeKernel khởi tạo được toàn bộ runtime services thông qua DI container.

Không service nào phải tự instantiate implementation dependency.

### AC-005-11 — Offline

Mock execution path chạy được offline, không yêu cầu external model/provider.

### AC-005-12 — Regression

Toàn bộ test của TASK-002 → TASK-004 vẫn PASS.

# TASK-006 — Model Contract + Provider Registry

## 1. Mục tiêu

Chuẩn hóa abstraction cho model và provider để AIOS **không bị khóa vào một vendor hoặc một runtime model cụ thể**.

TASK-006 tạo lớp contract chung giữa AIOS Runtime/Orchestrator và model providers:

```text
AIOS
 ↓
ModelContract
 ↓
ProviderRegistry
 ├── Mock
 ├── OpenAI
 └── Ollama
```

AIOS phải có khả năng thay đổi provider/model mà không thay đổi execution layer.

Đặc biệt, **Mock provider là bắt buộc** để đảm bảo deterministic testing và offline-first development.

---

## 2. Phạm vi

Định nghĩa contract chung cho model invocation.

Contract phải mô tả tối thiểu:

```text

provider
version

context_window
input/output interface
usage
cost
latency
error
availability
```

Model invocation phải trả về response chuẩn hóa thay vì expose vendor-specific response trực tiếp lên Orchestrator.

---

### 2.2 Provider Contract


Provider chỉ thực hiện request sau khi execution path đã được phép.

---

### 2.3 Provider Registry

Registry quản lý:

* provider registration;
* provider lookup;
* model discovery;
* model metadata;
* health/availability;
* provider version;

Ví dụ:


```yaml
  input_cost:
  output_cost:
```

### 2.5 Usage và Cost

Mỗi invocation cần thu thập usage:

```text

```

---

### 2.6 Error Model

Vendor-specific errors phải được normalize.

Ví dụ:

```text

AUTHENTICATION_ERROR
INVALID_REQUEST
MODEL_UNAVAILABLE
PROVIDER_ERROR
UNKNOWN
```

Không expose trực tiếp exception class của vendor ra toàn hệ thống.

---

### 2.7 Mock Provider

Mock provider phải:

* chạy hoàn toàn offline;
* deterministic;
* configurable response;
* configurable failure;
* configurable latency;
* tạo usage giả lập;
* dùng được trong unit/integration/simulation tests.

Ví dụ:

```text

```

Điều này là nền tảng cho testing/failure recovery sau này.

# TASK-007 — Memory + Knowledge

## 1. Mục tiêu

Xây nền tảng **Memory + Knowledge** cho AIOS, cho phép hệ thống lưu trữ, truy xuất và sử dụng thông tin có provenance thay vì phụ thuộc vào context tạm thời của một execution.

TASK-007 đặt nền móng cho bốn loại memory:

```text
Conversation Memory
Session Memory
Knowledge Memory
Artifact Memory
```

và knowledge pipeline:

```text
Source
 ↓
Indexer
 ↓
Chunks
 ↓
Metadata
 ↓
Embeddings / Index
 ↓
Knowledge Store
 ↓
Retriever
 ↓
Evidence
```

Mục tiêu quan trọng không chỉ là "tìm được text", mà phải biết **text đến từ đâu**, thuộc source nào và có thể truy nguyên.

---

## 2. Phạm vi

### 2.1 Conversation Memory

Lưu thông tin hội thoại cần thiết:

* user request;
* assistant response;
* relevant conversation turns;
* timestamps;
* session reference;
* metadata.

Conversation memory phải có lifecycle rõ ràng.

Không mặc định đưa toàn bộ lịch sử vào execution.

---

### 2.2 Session Memory

Lưu state/context của một session.

Ví dụ:

```text
session_id
goal
current task
active workflow
recent decisions
temporary context
```

Session memory phục vụ khả năng tiếp tục công việc trong cùng hoặc các execution liên quan.

---

### 2.3 Knowledge Memory

Lưu tri thức được ingest từ nguồn bên ngoài:

* local documentation;
* PDF;
* source code;
* text files;
* project documentation.

Knowledge phải giữ metadata/provenance.

---

### 2.4 Artifact Memory

Lưu reference tới artifact được tạo bởi hệ thống:

```text
artifact_id
type
version
checksum
source execution
created_at
metadata
```

Artifact memory không nhất thiết duplicate Artifact Service storage.

Nó có thể lưu reference tới artifact canonical.

---

## 2.5 Memory Lifecycle

Memory phải có lifecycle tối thiểu:

```text
CREATE
→ STORE
→ INDEX
→ RETRIEVE
→ UPDATE / VERSION
→ EXPIRE / ARCHIVE
```

Lifecycle phải phân biệt giữa:

* immutable artifact;
* session state;
* conversation history;
* indexed knowledge.

Không dùng một lifecycle duy nhất cho tất cả memory type.

---

## 2.6 Knowledge Indexer

Indexer chịu trách nhiệm đọc source và chuyển thành searchable representation.

Pipeline:

```text
Source
 ↓
Parser
 ↓
Document
 ↓
Chunker
 ↓
Chunk Metadata
 ↓
Embedding / Keyword Index
 ↓
Knowledge Store
```

Chunk phải giữ reference tới source.

Ví dụ:

```yaml
chunk:
  id:
  source_id:
  document_id:
  location:
  content_hash:
  metadata:
```

---

## 2.7 Local Sources

M1 phải ưu tiên offline/local sources.

Tối thiểu hỗ trợ:

* Markdown/text;
* PDF;
* source code;
* local documentation.

Không bắt buộc web ingestion trong TASK-007 nếu chưa có infrastructure phù hợp.

---

## 2.8 Retrieval

Retriever phải hỗ trợ ít nhất primitive:

```text
keyword
semantic
metadata
```

Kiến trúc phải cho phép mở rộng thành hybrid retrieval sau này.

Retriever không được hard-code vào một vector database cụ thể.

---

## 2.9 Provenance

Mọi knowledge result phải có provenance.

Ví dụ:

```text
Retrieved Chunk
 ↓
Document
 ↓
Source
 ↓
File / Location
```

Evidence tối thiểu phải truy được:

```text
source_id
document_id
chunk_id
location
content_hash
created_at
```

Nếu provenance không xác định được, result không được coi là authoritative evidence.

---

## 2.10 Memory Isolation

Memory phải có boundary giữa các memory types và execution/session.

Agent không được tự ý truy cập storage implementation.

Kiến trúc nền:

```text
Agent
 ↓
Memory API
 ↓
Memory Service
 ↓
Memory Store
```

Đây là tiền đề để M5 xây **Memory Coordinator**.

TASK-007 chưa triển khai Memory Coordinator đầy đủ.
