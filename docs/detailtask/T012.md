# M2 — TASK-012: Operational Orchestration

Theo master specification, TASK-012 tập trung vào **Goal Manager, Task Queue, Permission Broker và Failure Recovery**, với yêu cầu đặc biệt là goal phải persist/resume được và Task Queue không được bị trộn với Scheduler kỹ thuật. 

## 1. Mục tiêu

Xây lớp **Operational Orchestration** nằm giữa Decision Pipeline của TASK-010 và Runtime Kernel của M1.

TASK-010 trả lời:

> **“Request này nên được xử lý như thế nào?”**

TASK-012 bổ sung:

> **“Làm sao quản lý task đó trong suốt vòng đời, xin quyền, retry khi lỗi và tiếp tục được sau khi process/session kết thúc?”**

Luồng tổng thể:

```text
Request
   ↓
Decision Pipeline
   ↓
Execution Plan / Tasks
   ↓
Goal Manager
   ↓
Task Queue
   ↓
Permission Broker
   ↓
Runtime Execution
   ↓
Failure Recovery
   ↓
Result / Goal Progress
```

---

# 2. Phạm vi

TASK-012 gồm 4 subsystem:

```text
TASK-012
├── Goal Manager
├── Task Queue
├── Permission Broker
└── Failure Recovery
```

Các subsystem này **không được trở thành Runtime mới**.

Runtime vẫn chịu trách nhiệm execution thật; TASK-012 chỉ quản lý orchestration state và quyết định bước tiếp theo.

---

# 3. Goal Manager

## 3.1. Mục đích

Goal Manager quản lý các mục tiêu kéo dài qua nhiều task và nhiều phiên.

Ví dụ:

```text
Goal:
"Xây authentication module cho AIOS"
```

được phân thành:

```text
Goal
├── Analyze requirements
├── Design
├── Implement
├── Write tests
├── Run tests
└── Review
```

Mỗi task có thể tương ứng với một workflow/execution.

---

## 3.2. Goal Contract

Tối thiểu cần có:

```yaml
goal:
  id: goal-001
  title: Build authentication module
  description: ...
  status: ACTIVE

  tasks:
    - task-001
    - task-002
    - task-003

  created_at: ...
  updated_at: ...

  metadata:
    priority: normal
```

State của Goal phải persistent.

Không được chỉ giữ trong memory của Orchestrator process.

---

## 3.3. Goal lifecycle

```text
CREATED
   ↓
PLANNED
   ↓
ACTIVE
   ↓
PAUSED
   ↓
ACTIVE
   ↓
COMPLETED
```

Các trạng thái terminal:

```text
COMPLETED
FAILED
CANCELLED
```

Goal có thể:

* pause
* resume
* cancel
* retry task
* xem progress

---

## 3.4. Goal Progress

Goal Manager phải tính được:

```text
Goal Progress
= completed tasks / total executable tasks
```

Nhưng không được hiểu:

```text
80% task completed = Goal successful
```

Goal chỉ `COMPLETED` khi các acceptance condition cuối cùng đạt.

Ví dụ:

```text
8/10 tasks done
→ progress = 80%
→ goal status = ACTIVE
```

Nếu task quan trọng fail:

```text
8/10 done
1 failed
1 blocked
→ goal = BLOCKED/FAILED
```

# 4. Task Queue

## 4.1. Logical Queue

Task Queue là **queue logic của Orchestrator**, không phải Scheduler Service.

Đây là distinction bắt buộc:

```text
Task Queue
= "Task nào nên được xử lý tiếp?"

Scheduler Service
= "Execution được chạy vào thời điểm nào?"
```

Ví dụ:

```text
Goal Manager
    ↓
Task Queue
    ↓
Task A READY
Task B BLOCKED
Task C READY
    ↓
Execution Supervisor
    ↓
Scheduler Service
    ↓
Runtime
```

Task Queue **không được tự chạy process, cron hoặc workflow**.

---

# 5. Task Queue Contract

Task tối thiểu:

```yaml
task:
  id: task-001
  goal_id: goal-001

  status: READY
  priority: high

  dependencies:
    - task-000

  workflow_id: workflow-xyz

  created_at: ...
  updated_at: ...
```

Các trạng thái cần phân biệt:

```text
PENDING
READY
RUNNING
PAUSED
BLOCKED
SUCCEEDED
FAILED
CANCELLED
```

Dependency chưa hoàn thành:

```text
Task B
depends_on: Task A

Task A != SUCCEEDED
        ↓
Task B = BLOCKED/PENDING
```

---

# 6. Queue Operations

TASK-012 phải hỗ trợ ít nhất:

```text
enqueue()
dequeue()
peek()
pause()
resume()
reorder()
prioritize()
cancel()
block()
unblock()
```

Priority có thể gồm:

```text
CRITICAL
HIGH
NORMAL
LOW
```

Nhưng priority **không được override policy hoặc dependency**.

Ví dụ:

```text
Task A = LOW
Task B = HIGH
B depends on A
```

Không được chạy B trước A chỉ vì B có priority cao hơn.

# 7. Permission Broker

Permission Broker là lớp trung gian gom và xử lý permission requirements của workflow/task.

Luồng:

```text
Workflow
   ↓
Required Permissions
   ↓
Permission Broker
   ↓
Policy / Permission Service
   ↓
ALLOW / DENY / ASK
```

Permission Broker **không tự quyết định policy**.

Authority vẫn thuộc Policy/Permission layer của Runtime.

---

## 7.1. Permission aggregation

Một workflow có thể yêu cầu:

```yaml
permissions:
  - filesystem.read
  - filesystem.write
  - shell.execute
  - network.outbound
```

Broker phải:

1. collect
2. normalize
3. deduplicate
4. kiểm tra scope
5. chuyển sang Policy/Permission Service
6. trả decision

---

# 8. Permission Decision

Các kết quả chính:

```text
ALLOW
DENY
ASK
```

Nếu `DENY`:

```text
Task
 ↓
Permission Broker
 ↓
DENY
 ↓
Task BLOCKED
```

Không được:

```text
DENY
 ↓
Agent tự thử Tool khác
```

Nếu `ASK`:

```text
Task
 ↓
ASK
 ↓
Human Approval
 ↓
ALLOW / DENY
```

Approval phải có evidence.

---

# 9. Permission Scope

Permission phải gắn với execution context.

Ví dụ không chỉ:

```text
filesystem.write
```

mà có thể:

```yaml
permission:
  scope: filesystem.write
  target: workspace/project-a
  mode: scoped
```

TASK-012 chưa phải Enterprise Identity/Tenant system; các boundary enterprise sẽ mở rộng ở M7.

Do đó không được đưa multi-tenant logic vào TASK-012.

# 10. Failure Recovery

Failure Recovery xử lý execution failure theo policy.

Pipeline:

```text
Execution Failed
      ↓
Classify Failure
      ↓
Retry?
 ┌────┴────┐
Yes       No
 ↓         ↓
Retry    Fallback?
           ↓
        Report/Block
```

Roadmap yêu cầu recovery theo hướng:

```text
Retry
  ↓
Fallback Agent
  ↓
Fallback Workflow
  ↓
Report
```

nhưng chỉ được áp dụng nếu policy cho phép.

---

# 11. Failure Classification

Không phải mọi failure đều retry được.

Ví dụ:

```text
TRANSIENT
- timeout
- temporary unavailable
- connection reset

RESOURCE
- CPU exhausted
- memory unavailable

POLICY
- permission denied
- policy denied

VALIDATION
- invalid input
- invalid plan

LOGICAL
- workflow failure

FATAL
- corrupted state
- invalid contract
```

Ví dụ:

```text
timeout
→ retry

policy denied
→ KHÔNG retry mù quáng

invalid ExecutionPlan
→ reject / replan

corrupted state
→ recovery / block
```

---

# 12. Retry Policy

Retry phải deterministic và có giới hạn.

Ví dụ:

```yaml
retry:
  max_attempts: 3
  backoff:
    strategy: exponential
    initial_ms: 500
    max_ms: 5000
```

Runtime vẫn thực hiện retry execution-level nếu thuộc trách nhiệm Execution Service.

TASK-012 quản lý **orchestration-level recovery**, không duplicate retry engine của Runtime.

Đây là boundary rất quan trọng.

---

# 13. Recovery Strategy

Có thể định nghĩa:

```text
RETRY_SAME
RETRY_WITH_MODIFIED_INPUT
FALLBACK_AGENT
FALLBACK_WORKFLOW
PAUSE_FOR_HUMAN
FAIL
```

Ví dụ:

```text
Coder Agent failed
      ↓
Retry Coder
      ↓
still failed
      ↓
Fallback Workflow
      ↓
still failed
      ↓
BLOCKED
```

Không được tự động đổi workflow nếu policy không cho phép.

# 14. Persistence

Đây là một Acceptance Criteria quan trọng của TASK-012:

> **Goal phải resume được.**

Ví dụ process bị restart:

```text
Session 1
Goal ACTIVE
Task A SUCCEEDED
Task B RUNNING
Task C PENDING
       ↓
     CRASH
       ↓
Session 2
       ↓
Load Goal
       ↓
Restore Task State
       ↓
Resume / Recover
```

Không được dựa vào:

```text
Python object trong RAM
```

Persistence phải lưu tối thiểu:

```text
Goal
Task
Dependency
Status
Attempts
Recovery history
Permission decisions
Execution references
Timestamps
```

---

# 15. Không duplicate Runtime State

TASK-012 không được tạo state engine thứ hai.

Phân chia:

| Thành phần            | Authority               |
| --------------------- | ----------------------- |
| Goal Manager          | Goal lifecycle          |
| Task Queue            | Logical task scheduling |
| Runtime State Service | Execution state         |
| Scheduler Service     | Technical scheduling    |
| Execution Service     | Execution lifecycle     |
| Policy Service        | Policy decision         |
| Permission Service    | Permission enforcement  |

Goal Manager có thể **tham chiếu** execution:

```yaml
task:
  execution_id: exec-123
```

nhưng không sở hữu execution state thay Runtime.

# 17. Acceptance Criteria

### AC-012-01 — Goal persistence

Restart process không làm mất Goal state.

### AC-012-02 — Resume

Goal đang `ACTIVE/PAUSED` có thể resume đúng task state.

### AC-012-03 — Dependency

Task không được READY nếu dependency chưa đạt điều kiện.

### AC-012-04 — Queue separation

Task Queue không thực hiện cron/technical scheduling.

### AC-012-05 — Permission

Permission request phải đi qua Permission/Policy Service.

### AC-012-06 — Fail closed

`DENY` → task không được execute.

### AC-012-07 — Retry bounded

Không có infinite retry.

### AC-012-08 — Recovery policy

Fallback chỉ xảy ra khi policy cho phép.

### AC-012-09 — State authority

Goal/Task orchestration state không được thay thế Runtime execution state.

### AC-012-10 — Regression

Toàn bộ M1 + TASK-010 phải PASS.

# 18. Test Scenarios

### Scenario A — Resume Goal

```text
Goal
 ├── A = DONE
 ├── B = RUNNING
 └── C = PENDING

A = DONE
B = recoverable
C = PENDING
Goal = resumable
```

### Scenario B — Dependency

```text

Expected:
B = BLOCKED
C = BLOCKED
```

### Scenario C — Permission Deny

```text

 → filesystem.write
 → Policy
 → DENY

Expected:

Execution != started
Evidence = DENY
```

### Scenario D — Retry

```text
attempt 1 → timeout
attempt 2 → timeout
attempt 3 → success
```

Expected:

```text
status = SUCCEEDED
attempts = 3
```

### Scenario E — Retry exhausted

```text
attempt 1 → fail
attempt 2 → fail
attempt 3 → fail
```

Expected:

```text

no attempt 4
```

### Scenario F — Restart during recovery

```text
Failure
 ↓
Recovery scheduled
 ↓
process restart
 ↓
restore recovery state
```

Expected:

```text
Recovery resumes deterministically
```
