# M2 — Developer Edition (P3–P4)

M2 là milestone biến Runtime đã hoàn thiện ở M1 thành **một hệ thống có thể thực sự nhận request, quyết định cách xử lý, chọn worker/capability/tool và thực thi task**.

Nguồn roadmap xác định 6 task của M2: **TASK-010, TASK-012 → TASK-016**. 

Chuỗi năng lực chính:

```text
Request
  ↓
TASK-010 Decision Pipeline
  ↓
TASK-012 Operational Orchestration
  ↓
TASK-013 Worker Plane
  ↓
TASK-014 Capability / Tool
  ↓
TASK-015 Skill / Plugin
  ↓
TASK-016 Architecture Hardening
  ↓
M2 Developer Edition
```

Một nguyên tắc xuyên suốt M2: **Agent/Worker không được trở thành một Runtime thứ hai**. Worker chỉ làm nghiệp vụ; quyền truy cập hệ thống phải đi qua Capability + Runtime, đồng thời chịu Permission/Policy. Điều này kế thừa trực tiếp nguyên tắc Runtime-first của roadmap.

# TASK-010 — Decision Pipeline

## 1. Mục tiêu

Xây **AIOS Orchestrator v1 Decision Pipeline** — lớp quyết định trung tâm để biến một request chưa cấu trúc thành một **Execution Plan có thể đưa xuống Runtime**.

Pipeline phải ưu tiên deterministic path:

```text
Request
   ↓
Normalizer
   ↓
Rule Engine
   ↓
Workflow Matcher
   ↓
Planner LLM
   ↓
Execution Plan
```

Điểm quan trọng nhất của TASK-010 là **LLM không được trở thành router mặc định**.

Nếu request có thể giải quyết bằng rule hoặc workflow có sẵn, AIOS phải xử lý mà **không cần gọi LLM**. Chỉ khi deterministic path trả về `INSUFFICIENT` mới chuyển sang Planner LLM. Đây là yêu cầu cốt lõi của roadmap. 

---

## 2. Vấn đề TASK-010 giải quyết

M1 đã có:

* Runtime Kernel
* Execution Service
* Workflow Definition
* Workflow Compiler
* Capability Registry
* Model Provider Registry
* Memory/Knowledge
* Policy/Permission

Nhưng Runtime vẫn chưa có một **control plane thực sự quyết định**:

> Request này là gì?
> Có workflow nào phù hợp không?
> Có cần LLM không?
> Nếu cần LLM thì dùng nó để lập kế hoạch thế nào?
> Kết quả cuối cùng chuyển thành Execution Plan ra sao?

TASK-010 lấp khoảng trống đó.

# 3. Phạm vi

TASK-010 gồm 4 thành phần chính.

### 3.1 Normalizer

Nhận request từ CLI/API/UI và chuẩn hóa thành một schema thống nhất.

Ví dụ:

```text
"review project"
```

→

```yaml
intent: review_code
target:
  type: workspace
  value: current
mode: execute
```

Normalizer xử lý:

* alias
* command normalization
* parameter normalization
* default values
* target resolution
* mode
* priority
* metadata
* source channel

Normalizer **không gọi LLM**.

### 3.2 Rule Engine

Rule Engine xử lý các request có thể xác định bằng deterministic rules.

Ví dụ:

```text
"run tests"
"show system health"
"list skills"
"review code"
"diagnose runtime"
```

Rule Engine có thể trả:

```text
MATCHED
```

hoặc:

```text
INSUFFICIENT
```

Không được dùng LLM để giải quyết một request mà rule engine đã xác định được.

### 3.3 Workflow Matcher

Nếu Rule Engine không trực tiếp giải quyết request, Workflow Matcher tìm workflow/template/macro phù hợp trong Workflow Library.

Ví dụ:

```text
"Create CRUD API"
```

có thể match:

```text
crud-generator-v1
```

Khi match thành công:

```text
Request
 → Workflow Matcher
 → Existing Workflow
 → Execution Plan
```

không cần Planner LLM.

### 3.4 Planner LLM

Chỉ chạy khi:

```text
Rule Engine = INSUFFICIENT
AND
Workflow Matcher = NO_MATCH
```

Planner nhận:

* normalized request
* available capabilities
* workflow candidates
* relevant system metadata
* policy constraints
* resource constraints

và tạo:

```text
ExecutionPlan
```

Planner **không được trực tiếp execute tool**.

# 4. Execution Plan

Execution Plan là artifact trung gian giữa Orchestrator và Runtime.

Ví dụ:

```yaml
execution_plan:
  id: plan-001
  request_id: req-001

  nodes:
    - id: analyze
      capability: analyze_code

    - id: test
      capability: run_tests

    - id: report
      capability: generate_report

  edges:
    - analyze -> test
    - test -> report

  permissions:
    - filesystem.read

  resources:
    cpu: 1
    memory: 512MB

  policy:
    network: denied
```

Plan phải được validate trước khi Execution Service nhận nó.

# 5. Planner không được bypass Runtime

Luồng đúng:

```text
Planner
   ↓
Execution Plan
   ↓
Policy / Permission validation
   ↓
Runtime
   ↓
Capability
   ↓
Tool
```

Luồng sai:

```text
Planner
   ↓
subprocess()
```

hoặc:

```text
Planner
   ↓
Python Tool
```

hoặc:

```text
Agent
   ↓
filesystem
```

Những bypass này phải được TASK-016 phát hiện và chặn.

# 6. Deterministic Routing Contract

TASK-010 cần định nghĩa rõ trạng thái của từng tầng:

```text
Normalizer
    ↓
NormalizedRequest

Rule Engine
    ↓
MATCHED | INSUFFICIENT

Workflow Matcher
    ↓
MATCHED | NO_MATCH

Planner
    ↓
ExecutionPlan
```

Không được dùng trạng thái mơ hồ kiểu:

```text
maybe
probably
unknown → execute
```

Đặc biệt:

```text
UNKNOWN ≠ PASS
```

và:

```text
INSUFFICIENT ≠ ERROR
```

`INSUFFICIENT` chỉ có nghĩa là tầng deterministic hiện tại không đủ thông tin và cần chuyển tầng tiếp theo.

# 7. Planner Output Validation

LLM output không được tin trực tiếp.

Pipeline:

```text
LLM Output
   ↓
Schema Validation
   ↓
Contract Validation
   ↓
Capability Validation
   ↓
Permission Validation
   ↓
Policy Validation
   ↓
Resource Validation
   ↓
ExecutionPlan
```

Nếu validation fail:

```text
Planner output = INVALID
```

không được execute.

Có thể:

```text
Retry Planner
```

hoặc:

```text
Fallback / Human Approval / Fail
```

tùy policy.

---

# 8. Offline-first

TASK-010 phải hoạt động khi **không có LLM**.

Ví dụ:

```text
aiagent run tests
```

không cần:

```text
OpenAI
Ollama
DeepSeek
```

Nếu Rule Engine đã biết cách xử lý thì request vẫn phải chạy được.

Tương tự:

```text
aiagent workflow crud-api
```

nếu Workflow Library có workflow tương ứng thì cũng không cần LLM.

Chỉ request thực sự cần planning mới phụ thuộc Planner.

# 10. Acceptance Criteria

### AC-010-01 — Normalization

Cùng một request semantic phải tạo ra normalized representation ổn định.

### AC-010-02 — Deterministic routing

Request đã được Rule Engine nhận diện phải **không gọi LLM**.

### AC-010-03 — Workflow reuse

Nếu Workflow Matcher tìm thấy workflow phù hợp thì Planner không được gọi.

### AC-010-04 — Planner fallback

Planner chỉ được gọi khi:

```text
Rule = INSUFFICIENT
AND
Workflow = NO_MATCH
```

### AC-010-05 — Planner validation

Planner output invalid phải bị reject, không được đưa vào Runtime.

### AC-010-06 — Policy boundary

Execution Plan phải chịu Policy/Permission validation trước execution.

### AC-010-07 — Offline

Các request deterministic phải chạy được khi không có model provider.

### AC-010-08 — Evidence

Có thể truy nguyên quyết định:

```text
Request → Decision → Plan
```

### AC-010-09 — Architecture

Planner/Orchestrator không trực tiếp gọi Tool.

### AC-010-10 — Regression

Toàn bộ test của M1 vẫn PASS.
