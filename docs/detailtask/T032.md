## TASK-032 — Evaluation Harness + Metrics

Theo roadmap, TASK-032 thuộc **M6 – AIOS Harness**, nằm sau TASK-030/031 và trước TASK-033. Mục tiêu canonical là **đánh giá output và trajectory bằng evaluator suite**. 

### 1. Objective

Xây Evaluation Harness để AIOS trả lời được:

> **Execution có tốt đến mức nào, không chỉ có chạy thành công hay không?**

Phải đánh giá được cả:

* Final output
* Execution trajectory
* Tool usage
* Policy compliance
* Task completion
* Correctness
* Cost
* Latency
* Token usage

Và kết quả phải có **evidence + provenance**, có thể lưu và tái lập.

---

### 2. Scope

TASK-032 **không tạo evaluation system độc lập**.

Tích hợp với:

```text
TASK-029 Harness Kernel
        ↓
TASK-030 Evidence / Verification
        ↓
TASK-031 Scenario / Simulation
        ↓
TASK-032 Evaluation
        ↓
TASK-033 Benchmark / Regression
```

Evaluation phải sử dụng `HarnessRun`, `Evidence Package`, execution trace và artifacts đã có.

Nguồn xác định Evaluation Model theo thứ tự:

```text
Deterministic
    ↓
Semantic
    ↓
LLM Judge
    ↓
Human
    ↓
Composite
```

LLM Judge **không được là evaluator mặc định**. Đây là hệ quả trực tiếp của nguyên tắc deterministic-first trong roadmap.

---

### 3. Core Contracts

Nên chuẩn hóa tối thiểu các abstraction sau:

```text
EvaluationSuite
EvaluationCase
Evaluator
EvaluationInput
Metric
MetricResult
EvaluationResult
EvaluationReport
```

Một `EvaluationSuite` phải mô tả được:

```yaml
suite:
  id: coder-v1
  dataset: coding-golden-v3

  metrics:
    - task_completion
    - correctness
    - policy_compliance
    - tool_accuracy
    - cost
    - latency

  thresholds:
    task_completion: 0.90
    correctness: 0.85
    policy_compliance: 1.0
```

Cấu trúc này bám trực tiếp evaluation suite được định nghĩa trong master plan.

---

### 4. Evaluation Input

Evaluator không chỉ nhận `final_output`.

Input nên có dạng:

```text
EvaluationInput
├── request
├── normalized_request
├── execution_plan
├── execution_graph
├── events
├── tool_results
├── test_results
├── artifacts
├── final_output
└── policy/evidence data
```

Như vậy có thể đánh giá **trajectory**.

Ví dụ:

```text
Decision
 → Tool A
 → Tool B
 → Failure
 → Retry
 → Tool C
 → Final Output
```

Final answer đúng nhưng trajectory vi phạm policy hoặc dùng tool sai → **không được coi là hoàn toàn PASS**.

Roadmap gọi đây là **Trajectory Evaluation**. 

---

### 5. Metric Model

Mỗi metric nên có:

```text
Metric
├── id
├── version
├── evaluator
├── input requirements
├── scoring method
├── threshold
├── score
├── status
└── evidence_refs
```

Ví dụ:

```text
task_completion = 0.94
correctness      = 0.91
policy_compliance = 1.00
tool_accuracy    = 0.88
cost             = 0.72
latency          = 0.83
```

Không nên ép mọi metric về một `overall_score` duy nhất.

**Quan trọng:** một hard requirement như `policy_compliance = 1.0` phải được giữ độc lập với score tổng hợp.

---

### 6. Evaluator Types

#### A. Deterministic Evaluator

Ưu tiên cao nhất.

Ví dụ:

```text
exit_code == 0
tests_passed == true
required_artifact_exists == true
policy_violations == 0
coverage >= threshold
```

Không cần LLM.

#### B. Semantic Evaluator

Dùng similarity / semantic comparison khi deterministic không đủ.

#### C. LLM Judge

Chỉ dùng khi cần đánh giá chất lượng khó định lượng.

Bắt buộc lưu:

```text
model
model_version
prompt_version
temperature
input
output
score
```

Điều này cần thiết để đáp ứng **INV-020 — Evaluation Determinism**.

#### D. Human Evaluator

Cho các evaluation cần human judgement.

#### E. Composite Evaluator

Kết hợp nhiều evaluator:

```text
Deterministic
    +
Semantic
    +
LLM Judge
    +
Policy
    ↓
Composite Result
```

---

### 7. Evaluation Result

Không nên chỉ trả:

```json
{"success": true}
```

Mà phải có dạng semantic tương đương:

```text
EvaluationResult
├── evaluation_id
├── run_id
├── suite_id
├── suite_version
├── status
├── metrics[]
├── threshold_results[]
├── trajectory_result
├── evidence_refs[]
├── evaluator_metadata
└── created_at
```

Status nên phân biệt:

```text
PASS
PASS_WITH_WARNING
FAIL
INCONCLUSIVE
```

Đặc biệt:

> `UNKNOWN` hoặc `INCONCLUSIVE` không được tự động nâng thành PASS.

Điều này phù hợp nguyên tắc Evidence-First của master specification. 

---

### 8. Evidence & Reproducibility

Mỗi evaluation result phải truy được:

```text
Evaluation
   ↓
HarnessRun
   ↓
Evidence Package
   ↓
Execution Trace
   ↓
Artifacts / Tests / Tool Results
```

Nếu dùng LLM Judge:

```text
Evaluation
 ├── model
 ├── model version
 ├── prompt version
 ├── temperature
 ├── input hash
 ├── raw output/artifact
 └── score
```

Không được có kiểu:

```text
"LLM nói score = 0.91"
```

mà không biết score được tạo từ đâu.

---

### 9. Trajectory Evaluation

Đây là phần quan trọng nhất của TASK-032.

Ví dụ:

```text
Request
  ↓
Decision
  ↓
Tool A
  ↓
Policy DENY
  ↓
Retry
  ↓
Tool B
  ↓
Correct Result
```

Kết quả:

```text
Final Correct: YES
Trajectory: WARNING
Policy violation: YES
Recovery: SUCCESS
```

Không được biến thành:

```text
PASS
```

chỉ vì output cuối đúng.

Evaluation phải phản ánh **chất lượng của cả quá trình**, không chỉ endpoint.

---

### 10. Deterministic Test Matrix

Tối thiểu nên có:

| Case                                   | Expected                 |
| -------------------------------------- | ------------------------ |
| Output đúng + trajectory đúng          | PASS                     |
| Output sai                             | FAIL                     |
| Output đúng nhưng tool sai             | WARNING/FAIL theo policy |
| Policy violation                       | FAIL                     |
| Missing evidence                       | INCONCLUSIVE             |
| Threshold không đạt                    | FAIL                     |
| LLM Judge thiếu metadata               | FAIL                     |
| Evaluation reproducibility mismatch    | FAIL                     |
| Multiple metrics, một hard metric fail | FAIL                     |
| Không có evaluator phù hợp             | INCONCLUSIVE             |

---

### 11. Architecture Constraints

TASK-032 phải giữ:

**INV-017 — Harness Isolation**

Harness không truy cập trực tiếp implementation nội bộ Runtime.

```text
Harness
  ↓ API / Contract
Runtime / Orchestrator
```

**INV-018 — Evidence First**

Mọi evaluation phải có evidence truy xuất được.

**INV-019 — Verification Before Verdict**

Không được suy ra PASS chỉ từ execution success.

**INV-020 — Evaluation Determinism**

LLM evaluation phải lưu đủ metadata để reproducible.

**INV-021 — Release Gate**

TASK-032 tạo evaluation result; **TASK-033** mới sử dụng nó để benchmark/regression gate.

Không được để TASK-032 tự biến thành release controller.

---

### 12. Test Strategy

Theo roadmap, test phải đi theo:

```text
Unit
 → Contract
 → Integration
 → Architecture
 → E2E
 → Regression
```

Các test quan trọng:

1. Deterministic evaluator trả score chính xác.
2. Threshold evaluation đúng.
3. Composite evaluator kết hợp đúng.
4. Trajectory evaluator đọc execution trace.
5. Evidence provenance không bị mất.
6. LLM Judge metadata đầy đủ.
7. Cùng input + cùng evaluator config → reproducible result.
8. Missing evidence → không PASS.
9. Policy violation → evaluation phản ánh FAIL.
10. TASK-029/030/031 regression vẫn PASS.
