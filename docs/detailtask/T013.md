# M2 — TASK-013: Worker Plane

Theo Master Task Specification, TASK-013 có mục tiêu tạo **General, Coder, Doctor và System Doctor workers**; phạm vi gồm **Agent Contract, lifecycle, capability access, result/evidence**. Acceptance cốt lõi: **Worker không được truy cập Runtime/Tool trực tiếp, chỉ qua Capability + Runtime**. 

---

## 1. Mục tiêu

Xây **Worker Plane** làm lớp thực thi nghiệp vụ phía trên Orchestrator.

Worker nhận một nhiệm vụ đã được orchestration quyết định, sử dụng các Capability được cấp và trả về **Result + Evidence**.

Kiến trúc bắt buộc:

```text
Request
   ↓
Decision Pipeline
   ↓
Goal / Task
   ↓
Worker
   ↓
Capability
   ↓
Policy / Permission
   ↓
Runtime
   ↓
Tool
```

Worker **không phải Runtime**, không phải Policy Engine và không phải Tool Router.

---

# 2. Bốn Worker ban đầu

TASK-013 yêu cầu bốn worker:

```text
General Worker
Coder Worker
Doctor Worker
System Doctor Worker
```

### General Worker

Worker tổng quát cho các task không thuộc domain chuyên biệt.

Ví dụ:

```text
research
summarize
transform
inspect
coordinate
```

General Worker không được tự ý thực thi capability ngoài capability contract của task.

---

### Coder Worker

Chuyên xử lý coding tasks:

```text
inspect code
edit code
run tests
analyze failure
refactor
```

Nhưng Coder Worker **không được trực tiếp**:

```python
subprocess.run(...)
open(...)
requests.get(...)
docker...
```

Mọi hành động phải đi qua Capability Layer.

---

### Doctor Worker

Xử lý chẩn đoán ở cấp application/task:

```text
diagnose task failure
inspect execution result
analyze logs
identify likely cause
recommend recovery
```

Doctor Worker chủ yếu **diagnose**, không mặc định có quyền sửa hệ thống.

---

### System Doctor Worker

Chẩn đoán Runtime/system:

```text
runtime health
service health
dependency health
configuration
architecture violations
readiness
```

System Doctor có thể phát hiện vấn đề nhưng quyền remediation vẫn thuộc Runtime/Policy/Orchestrator tương ứng.

---

# 3. Worker Contract

Mọi Worker phải tuân thủ một contract chung.

Ví dụ:

```yaml
worker:
  id: coder
  version: "1.0"

  capabilities:
    - code.read
    - code.write
    - test.run

  lifecycle:
    state: READY
```

Worker contract tối thiểu phải định nghĩa:

```text
worker_id
worker_type
version
capabilities
input_schema
output_schema
lifecycle
execution_context
policy_context
evidence_contract
```

Không được để mỗi worker tự định nghĩa một execution model riêng.

---

# 4. Worker Input

Worker không nhận raw user request trực tiếp nếu request đã đi qua Orchestrator.

Input nên có dạng:

```yaml
worker_request:
  task_id: task-001
  goal_id: goal-001

  objective:
    description: "Fix failing authentication tests"

  constraints:
    allowed_capabilities:
      - code.read
      - code.write
      - test.run

  context:
    workspace: project-a

  policy_context:
    network: denied
```

Worker chỉ được hoạt động trong context được cấp.

---

# 5. Capability Boundary

Đây là boundary quan trọng nhất của TASK-013.

### Được phép

```text
Worker
   ↓
Capability API
   ↓
Runtime
```

### Không được phép

```text
Worker
   ↓
Tool
```

hoặc:

```text
Worker
   ↓
Runtime internal API
```

hoặc:

```text
Worker
   ↓
filesystem / subprocess / provider
```

Master specification xác định Architecture Guard phải enforce boundary:

```text
Agent → Orchestrator → Runtime → Capability → Tool
```

và agent không được import trực tiếp `subprocess`, provider hay filesystem adapter. 

---

# 6. Capability Visibility

Worker **không nhìn thấy toàn bộ Tool Registry**.

Worker chỉ thấy:

```text
Allowed Capabilities
```

Ví dụ:

```yaml
allowed_capabilities:
  - code.read
  - code.write
  - test.run
```

Không phải:

```yaml
tools:
  - shell
  - python
  - docker
  - git
  - filesystem
  - http
```

Điều này giúp giữ abstraction:

```text
Worker
  biết "test.run"

không cần biết
  "pytest subprocess adapter"
```

---

# 7. Worker Lifecycle

Worker phải có lifecycle rõ ràng.

Đề xuất:

```text
REGISTERED
    ↓
READY
    ↓
ASSIGNED
    ↓
RUNNING
    ↓
COMPLETING
    ↓
COMPLETED
```

Failure:

```text
RUNNING
   ↓
FAILED
   ↓
RECOVERING
   ↓
READY / FAILED
```

Terminal:

```text
COMPLETED
FAILED
CANCELLED
```

Worker lifecycle không được trộn với Task lifecycle.

Ví dụ:

```text
Task = FAILED
```

không đồng nghĩa:

```text
Worker = FAILED
```

Worker có thể vẫn `READY` để nhận task tiếp theo.

---

# 8. Worker Execution Context

Mỗi execution phải có context riêng:

```yaml
execution_context:
  run_id: run-001
  task_id: task-001
  worker_id: coder
  capability_scope:
    - code.read
    - code.write
  permissions:
    - filesystem.workspace
```

Context này được truyền xuống Capability/Runtime.

Worker không được tự mở rộng scope.

Ví dụ:

```text
Worker được cấp:
code.read
```

không được tự yêu cầu:

```text
network.outbound
```

rồi sử dụng luôn.

Nếu cần permission mới:

```text
Worker
 ↓
Permission Request
 ↓
Policy
 ↓
ALLOW / DENY
```

---

# 9. Worker Result

Worker không chỉ trả text.

Result phải có cấu trúc:

```yaml
worker_result:
  status: SUCCEEDED

  output:
    summary: "Authentication tests fixed"

  artifacts:
    - artifact_id: artifact-001

  evidence:
    - evidence_id: evidence-001

  metrics:
    duration_ms: 4200

  execution:
    run_id: run-001
```

Các trạng thái chính:

```text
SUCCEEDED
FAILED
BLOCKED
CANCELLED
PARTIAL
```

`PARTIAL` không được tự động nâng thành `SUCCEEDED`.

---

# 10. Evidence

Worker phải tạo evidence khi kết quả cần được kiểm chứng.

Ví dụ Coder Worker:

```text
Code changed
   ↓
Test executed
   ↓
Test result
   ↓
Evidence
```

Evidence phải giữ provenance.

Master specification yêu cầu evidence có provenance chain:

```text
Evidence
  → Run
  → Artifact
  → Task
  → Requirement
```

và UNKNOWN không được nâng thành PASS. 

---

# 11. Ví dụ Coder Worker

Request:

```text
Fix failing test_login()
```

Flow:

```text
Coder Worker
    ↓
code.read
    ↓
Runtime
    ↓
filesystem adapter
    ↓
source
```

Sau đó:

```text
Coder Worker
    ↓
code.write
    ↓
Runtime
```

Sau cùng:

```text
Coder Worker
    ↓
test.run
    ↓
Runtime
    ↓
pytest
```

Result:

```yaml
status: SUCCEEDED

evidence:
  - tests_passed: true
  - changed_files: 2
```

Worker không tự gọi `pytest`.

---

# 12. Doctor Worker

Doctor Worker nhận failure:

```yaml
failure:
  run_id: run-001
  error_type: TEST_FAILURE
```

Nó có thể:

```text
inspect logs
inspect artifacts
inspect test results
analyze failure
```

và trả:

```yaml
diagnosis:
  category: DEPENDENCY_ERROR
  confidence: ...
  recommendation:
    - update dependency
```

Nhưng recommendation **không đồng nghĩa execution**.

Nếu muốn remediation:

```text
Doctor
 ↓
Recommendation
 ↓
Orchestrator
 ↓
New Task / Recovery
```

Doctor không tự bypass orchestration.

---

# 13. System Doctor

System Doctor tương tự nhưng phạm vi là Runtime/system.

Ví dụ:

```text
Runtime unhealthy
Service unavailable
Capability unhealthy
Policy configuration invalid
Architecture violation
```

Output:

```yaml
diagnosis:
  severity: HIGH
  status: DEGRADED

findings:
  - service: capability_router
    state: UNHEALTHY

recommendations:
  - restart capability service
```

System Doctor chỉ **đề xuất** remediation nếu không có capability/policy được cấp để thực hiện.

---

# 14. Worker Routing Contract

Orchestrator cần chọn Worker dựa trên task type/capability.

Ví dụ:

```text
coding task
    ↓
Coder Worker

diagnostic task
    ↓
Doctor Worker

runtime diagnostic
    ↓
System Doctor

generic task
    ↓
General Worker
```

Routing không nên dựa hoàn toàn vào tên Worker.

Nên dựa trên:

```text
task type
required capabilities
worker health
policy
availability
```

---

# 15. Worker Health

Worker phải expose health/readiness tối thiểu:

```text
REGISTERED
READY
BUSY
DEGRADED
UNAVAILABLE
```

Ví dụ:

```text
Coder Worker = UNAVAILABLE
```

Orchestrator không assign task mới cho worker đó.

Có thể fallback sang worker khác **chỉ khi capability/policy cho phép**.

---

# 16. Worker Isolation

Worker phải được isolation khỏi:

* Runtime internals
* Tool implementation
* Model provider implementation
* Policy implementation
* Credential store
* filesystem adapters

Worker chỉ tương tác qua public contracts.

Điều này giúp TASK-016 có thể dùng AST/import tests để phát hiện architecture violation. Master specification quy định architecture violation phải làm gate FAIL.

# 18. Acceptance Criteria

### AC-013-01 — Worker Contract

Bốn worker cùng tuân thủ một contract chung.

### AC-013-02 — Capability-only access

Worker không gọi Tool trực tiếp.

### AC-013-03 — Runtime boundary

Worker không bypass Runtime.

### AC-013-04 — Permission boundary

Worker không tự cấp permission.

### AC-013-05 — Lifecycle

Worker lifecycle được state machine kiểm soát.

### AC-013-06 — Result

Mọi execution đều trả structured result.

### AC-013-07 — Evidence

Kết quả quan trọng có evidence/provenance.

### AC-013-08 — Routing

Task được route đến worker phù hợp dựa trên contract/capability.

### AC-013-09 — Failure

Worker failure được trả về Orchestrator/Failure Recovery, không tự tạo control plane.

### AC-013-10 — Architecture

AST/import architecture tests chứng minh không có:

```text
Worker → Tool
Worker → subprocess
Worker → Provider
Worker → filesystem adapter
```

### AC-013-11 — Regression

M1 + TASK-010 + TASK-012 phải PASS.

### Kết quả của TASK-013

Sau TASK-013, AIOS có cấu trúc rõ:

```text
                 ┌──────────────┐
                 │ Orchestrator │
                 └──────┬───────┘
                        ↓
              ┌──────────────────┐
              │   Worker Plane   │
              ├──────────────────┤
              │ General          │
              │ Coder            │
              │ Doctor           │
              │ System Doctor    │
              └────────┬─────────┘
                       ↓
                 Capability
                       ↓
                    Runtime
                       ↓
                     Tool
```

**Worker là lớp nghiệp vụ; Runtime vẫn là control substrate.** Đây là boundary mà TASK-014 sẽ tiếp tục củng cố khi chuẩn hóa **Python / Docker / REST / MCP / Shell / Git** thành các Tool Adapter phía dưới Capability Layer.
