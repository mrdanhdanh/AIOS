# TASK-026 — Planning Engine

## 1. Mục tiêu

Xây dựng **Planning Engine** để biến một Goal/Request phức tạp thành một `ExecutionPlan` có cấu trúc, có dependency, capability, resource, policy và risk rõ ràng.

Pipeline mục tiêu:

```text
Goal
 ↓
Goal Analyzer
 ↓
Task Decomposer
 ↓
Dependency Analyzer
 ↓
Capability Resolver
 ↓
Risk Analyzer
 ↓
Execution Planner
 ↓
Plan Validator
 ↓
ExecutionPlan
```

Planning Engine không trực tiếp execute task.

## 3. Nguyên tắc thiết kế

### 3.1 Deterministic First

Planning không mặc định dùng LLM.

Thứ tự:

```text
Known Workflow
      ↓
Template Planning
      ↓
Rule Planning
      ↓
LLM Planning
```

Nếu Workflow Library đã có workflow phù hợp thì reuse trước.

Task đơn giản và đã biết → không gọi LLM.

Chỉ dùng LLM khi deterministic planner không đủ.

---

### 3.2 Planning không phải Execution

Planning Engine chỉ tạo:

```text
ExecutionPlan
```

Không được:

```text
Planning Engine
 → Tool
 → subprocess
 → filesystem
 → execute
```

Execution vẫn thuộc Runtime.

---

### 3.3 Plan phải validate trước execution

Không có đường:

```text
Planner → Runtime
```

mà phải:

```text
Planner
 ↓
Plan Validator
 ↓
Policy / Permission validation
 ↓
Resource validation
 ↓
ExecutionPlan
 ↓
Runtime
```

Đây là cơ sở trực tiếp của **INV-014 — Plan Validation**.

# 4. Goal Analyzer

Goal Analyzer xác định:

* goal;
* objective;
* target;
* constraints;
* expected output;
* success conditions;
* priority;
* deadline nếu có;
* resource constraints;
* policy requirements.

Ví dụ:

```text
"Review authentication module và viết test"
```

được chuẩn hóa thành:

```yaml
goal:
  objective: review_authentication
  target: authentication_module
  outputs:
    - review_report
    - test_files
  constraints:
    - no_production_changes
```

Goal Analyzer không tự thực hiện task.

---

# 5. Task Decomposer

Chuyển goal thành các task nhỏ hơn.

Ví dụ:

```text
Goal:
Review authentication module và viết test
```

→

```text
T1 Analyze authentication module

T2 Identify security issues
T3 Identify missing tests

T4 Write tests

T5 Run tests

T6 Generate report
```

Dependency:

```text
T1
├── T2
└── T3
     ↓
    T4
     ↓
    T5
     ↓
    T6
```

T2 và T3 có thể chạy song song nếu không có dependency khác.

---

# 6. Task Contract

Mỗi planned task tối thiểu có:

```yaml
task:
  id: T1
  name: analyze_authentication
  objective: Analyze authentication module

  inputs:
    - workspace

  outputs:
    - analysis_report

  required_capabilities:
    - filesystem.read

  resources:
    cpu: 1
    memory_mb: 512

  permissions:
    - filesystem.read

  timeout: 300

  retry:
    max_attempts: 2
```

Task ID phải ổn định trong phạm vi execution plan.

---

# 7. Dependency Analyzer

Dependency Analyzer xác định quan hệ giữa task.

Các loại dependency tối thiểu:

```text
DATA
CONTROL
RESOURCE
CONDITION
```

Ví dụ:

```text
T1 → T2
```

nghĩa là T2 không được READY trước khi T1 hoàn thành.

Planner phải phát hiện cycle:

```text
T1 → T2
T2 → T3
T3 → T1
```

và reject plan.

Việc chuyển plan thành DAG chính thức thuộc TASK-027, nhưng TASK-026 phải phát hiện dependency invalid trước khi tạo ExecutionPlan.

---

# 8. Capability Resolver

Mỗi task phải khai báo capability cần thiết.

Ví dụ:

```text
Write test
→ filesystem.write
→ execute_code
→ run_tests
```

Resolver tìm capability tương ứng trong Capability Registry.

Không chọn Tool trực tiếp.

Đúng:

```text
Planning Engine
 ↓
Capability
```

Không:

```text
Planning Engine
 ↓
PythonTool
```

Tool selection vẫn thuộc Capability Router/Runtime.

---

# 9. Resource Estimator

Planner cần estimate resource trước execution:

```yaml
resources:
  cpu: 2
  memory_mb: 2048
  gpu: 0
  tokens: 12000
  timeout_seconds: 600
```

Estimate không phải allocation.

Phân biệt:

```text
Planning
= estimate

Resource Service
= grant / queue / reject
```

Planning Engine không được chiếm resource thật.

---

# 10. Risk Analyzer

Mỗi plan cần có risk information.

Risk có thể xuất phát từ:

* filesystem write;
* shell;
* network;
* Docker;
* credential;
* production target;
* destructive operation;
* high resource consumption;
* external model;
* missing verification.

Ví dụ:

```yaml
risk:
  level: HIGH
  reasons:
    - filesystem.write
    - shell.execute
  requires_approval: true
```

Risk Analyzer không tự approve.

Decision vẫn thuộc Policy/Permission layer.

# 14. LLM Planning

LLM chỉ được dùng khi:

```text
Known Workflow = unavailable
AND
Template Planner = insufficient
AND
Rule Planner = insufficient
```

Flow:

```text
Deterministic Planner
        ↓
   INSUFFICIENT
        ↓
    Model Router
        ↓
      LLM
        ↓
Plan Parser
        ↓
Plan Validator
```

LLM output không bao giờ được xem là ExecutionPlan hợp lệ ngay lập tức.

---

# 15. LLM Output Boundary

LLM chỉ được trả về structured candidate:

```json
{
  "tasks": [],
  "dependencies": [],
  "capabilities": [],
  "resources": {}
}
```

Sau đó:

```text
LLM Output
 ↓
Schema Validation
 ↓
Semantic Validation
 ↓
Policy Validation
 ↓
Dependency Validation
 ↓
ExecutionPlan
```

Nếu validation fail:

```text
INVALID_PLAN
```

không execution.

# 17. Adaptive Planning

Không phải request nào cũng chạy full pipeline.

### Simple

```text
Request
 → Rule
 → Existing Workflow
 → Execution
```

### Medium

```text
Request
 → Memory
 → Context
 → Template/Rule Planner
 → Execution
```

### Complex

```text
Request
 → Memory
 → Context
 → Model Router
 → LLM Planner
 → Plan Validator
 → ExecutionGraph
 → Scheduler
 → Runtime
```

Đây là yêu cầu quan trọng để M5 không biến thành pipeline nặng cho mọi request.
