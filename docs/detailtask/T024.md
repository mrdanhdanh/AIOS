## TASK-024 — Context Optimizer

## 1. Metadata

* **Milestone:** M5 — Core Intelligence
* **Task ID:** TASK-024
* **Tên:** Context Optimizer
* **Mục tiêu canonical:** Tối ưu context theo relevance, budget và lifecycle.
* **Dependency trực tiếp:** TASK-023 — Memory Coordinator
* **Priority:** High
* **Status:** PLANNED
* **Execution model:** Runtime-first · Policy-first · Evidence-first · Fail-closed


TASK-024 thuộc **M5 – Core Intelligence**, đứng sau TASK-023 Memory Coordinator. Vai trò của nó là biến tập memory đã được chọn thành **context tối ưu để đưa vào model**, không thay thế Memory Coordinator. Theo roadmap, mục tiêu chính là tối ưu context theo **relevance, budget và lifecycle**. 

### 1. Mục tiêu

Context Optimizer phải giải quyết câu hỏi:

> **Trong những thông tin Memory Coordinator đã lấy được, thông tin nào cần đưa vào execution hiện tại, bao nhiêu là đủ, và nên biểu diễn như thế nào?**

Ranh giới trách nhiệm:

```text
Memory Coordinator
    ↓
Retrieve → Filter → Rank
    ↓
Context Optimizer
    ↓
Deduplicate → Compress → Prioritize → Budget
    ↓
Final Context
    ↓
Context Service / Model
```

Memory Coordinator quyết định **lấy memory nào**; Context Optimizer quyết định **dùng bao nhiêu và dùng theo dạng nào**.

### 3. Context Priority

Context phải có priority cố định để xử lý thiếu budget.

| Priority | Nội dung                |
| -------- | ----------------------- |
| P0       | System / Safety         |
| P1       | User Request            |
| P2       | Current Execution State |
| P3       | Relevant Knowledge      |
| P4       | Relevant Memory         |
| P5       | Historical              |
| P6       | Optional                |

Khi budget không đủ, loại bỏ **từ P6 lên P0**, không truncate ngẫu nhiên.

Ví dụ:

```text
Budget = 20K

P0 System/Safety       3K
P1 User Request        2K
P2 Execution State     2K
P3 Knowledge           6K
P4 Memory              5K
P5 Historical          1K
P6 Optional            1K
                       ──
                       20K
```

Nếu chỉ còn 12K:

```text
P0 + P1 + P2 + P3 + P4
→ cắt P6
→ giảm P5
→ sau đó mới giảm P4
```

Không được hy sinh System/Safety hoặc User Request chỉ vì context lớn.

---

### 4. Context Deduplication

Context Optimizer phải phát hiện thông tin trùng lặp.

Các trường hợp cần xử lý:

* cùng một memory xuất hiện nhiều lần
* cùng artifact được retrieve qua nhiều nguồn
* message history chứa nội dung đã có trong summary
* knowledge fragments overlap
* metadata lặp lại nhưng không mang giá trị

Ví dụ:

```text
Memory A:
"Oracle TIMESTAMP dùng timezone..."

Memory B:
"Oracle TIMESTAMP cần xử lý timezone..."

Knowledge:
"Oracle TIMESTAMP WITH TIME ZONE..."
```

Không đưa nguyên trạng cả ba vào model nếu chúng chứa cùng một thông tin.

Kết quả phải giữ:

```text
content
source
provenance
importance
timestamp
```

để không mất khả năng truy nguyên.

### 5. Context Compression

Compression phải tuân thủ:

**Deterministic First → LLM Last**

#### Level 1 — Deterministic

Không dùng LLM.

Thực hiện:

* remove duplicate
* remove metadata dư thừa
* merge fragments
* loại message cũ
* loại nội dung đã được superseded
* chuẩn hóa representation

Đây phải là đường mặc định.

#### Level 2 — Extractive

Chỉ giữ phần liên quan.

Ví dụ:

```text
Original document = 8K tokens

Relevant sections:
- Oracle timestamp
- timezone conversion
- failing query

→ Context = 2K tokens
```

Không sinh nội dung mới.

#### Level 3 — LLM Compression

Chỉ sử dụng khi:

* deterministic compression chưa đủ
* context vẫn vượt budget
* policy cho phép LLM compression

LLM output phải được coi là **derived artifact**, có provenance.

Không được biến summary thành source-of-truth thay cho dữ liệu gốc.

### 6. Context Budget

Context Optimizer phải nhận budget rõ ràng.

Ví dụ contract:

```yaml
context_budget:
  max_tokens: 20000
  reserve_tokens: 1000
```

Optimizer phải bảo đảm:

```text
final_context_tokens
+
reserve_tokens
≤
max_tokens
```

Nếu không thể đáp ứng:

```text
OPTIMIZATION_FAILED
```

hoặc trả về context với trạng thái rõ ràng theo contract.

Không được âm thầm vượt budget.

Đây chính là cơ sở của **INV-012 — Context Budget** trong M5. Master Plan yêu cầu Context có budget + priority và phải đo được context size/compression. 

---

### 7. Lifecycle

Context không phải dữ liệu tồn tại vĩnh viễn.

Mỗi context item cần lifecycle metadata, ví dụ:

```text
CREATED
ACTIVE
STALE
EXPIRED
SUPERSEDED
REMOVED
```

Optimizer phải ưu tiên:

```text
ACTIVE > STALE > HISTORICAL
```

và loại bỏ item:

* hết TTL
* superseded
* không còn liên quan
* duplicate
* không còn hợp lệ với execution hiện tại

Context cũ không được mặc nhiên xem là sự thật hiện tại.

### 15. Dependency / Gate

Dependency trực tiếp:

```text
TASK-023 Memory Coordinator
        ↓
TASK-024 Context Optimizer
        ↓
TASK-025 Model Router
```

TASK-024 **không nên bắt đầu implement trước khi TASK-023 cung cấp contract ổn định**, vì Context Optimizer nhận `MemoryContext` từ Memory Coordinator.

Theo workflow bắt buộc của AIOS, task phải đi đủ:

```text
PLAN
→ SPEC
→ CRITIQUE ×2
→ BREAKDOWN
→ REVIEW
→ IMPLEMENT
→ TEST
→ EVALUATE
→ REGRESSION
→ COMMIT
```

Task chỉ được DONE khi toàn bộ gate đạt PASS; hệ thống governance quy định thiếu artifact bắt buộc hoặc regression failure thì không được đóng task. 

**Kết luận:** TASK-024 là lớp **Context Intelligence** nằm giữa Memory và Model. Nó không "lấy thêm dữ liệu", mà biến dữ liệu đã retrieve thành **context nhỏ nhất nhưng đủ dùng, có priority, có budget, có lifecycle và có provenance**. Đây là tiền đề trực tiếp cho TASK-025 Model Router và toàn bộ Planning/Execution Intelligence của M5.
