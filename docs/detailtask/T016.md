# TASK-016 — Architecture Hardening

## 1. Mục tiêu

Xây dựng **Architecture Hardening Gate** để biến các architecture invariant của AIOS từ quy ước thiết kế thành các quy tắc có thể kiểm tra tự động.

TASK-016 phải bảo đảm rằng khi codebase phát triển, các vi phạm sau không thể âm thầm lọt qua:

* Agent truy cập Tool trực tiếp.
* Agent bypass Capability.
* Workflow phụ thuộc trực tiếp vào execution engine.
* Execution bypass Policy/Permission.
* Orchestrator trở thành God Object.
* Các layer import ngược hoặc tạo dependency cycle.
* Component truy cập implementation nội bộ thay vì contract.
* Deterministic control path bị bypass bởi LLM.
* Capability Router chọn Tool trực tiếp thay vì thông qua Capability contract.
* Plugin/Skill xâm nhập Core trái với boundary.

Nguyên tắc cốt lõi:

> **Architecture violation = gate FAIL = task/release không được PASS.**

TASK-016 không chỉ tạo test suite; nó tạo **enforcement mechanism** để architecture được bảo vệ liên tục trong CI và regression.

## 3. Phạm vi

### 3.1. Architecture rule engine

Xây tập rule kiểm tra architecture bằng AST/import analysis.

Mỗi rule có:

```text
rule_id
description
severity
source_layer
target_layer
allowed / denied
evidence
```

Ví dụ:

```text
ARCH-001
Agent → Tool direct import
Severity: ERROR
Expected: DENY
```

---

### 3.2. Layer dependency validation

Xác định architecture layer chính:

```text
UI
 ↓
API
 ↓
Orchestrator
 ↓
Runtime
 ↓
Capability
 ↓
Tool
```

Các dependency hợp lệ phải đi theo boundary contract.

Không cho phép dependency ngược kiểu:

```text
Tool → Orchestrator
Tool → Agent
Capability → Agent
Agent → Tool implementation
```

hoặc import xuyên tầng mà không có contract boundary.

---

### 3.3. Agent boundary

Worker Agent chỉ được sử dụng:

```text
Agent
  ↓
Capability
  ↓
Runtime / Tool execution boundary
```

Không được:

```python
import subprocess
import requests
import docker
import filesystem_adapter
```

để tự thực thi infrastructure/tool operation.

Agent cũng không được truy cập trực tiếp:

* Runtime Service implementation.
* Tool Registry implementation.
* Provider implementation.
* Filesystem adapter.
* Docker client.
* Shell executor.

---

### 3.4. Capability boundary

Capability là abstraction giữa Agent và Tool.

Một Agent chỉ yêu cầu:

```text
execute_code
run_tests
filesystem.read
git.diff
```

thay vì:

```text
PythonTool
ShellTool
GitTool
```

Architecture test phải phát hiện việc Agent hard-code Tool implementation.

---

### 3.5. Workflow/Engine independence

Workflow Definition phải độc lập workflow engine.

Không cho phép:

```text
Workflow Definition
    ↓
LangGraph implementation
```

theo kiểu hard dependency.

Thay vào đó:

```text
Workflow Definition
        ↓
Compiler Interface
   ┌────┴────┐
LangGraph  Mock
```

Architecture test phải phát hiện import trực tiếp engine implementation từ domain workflow contract.

Điều này duy trì quyết định **engine independence** của AIOS.

---

### 3.6. Policy/Permission boundary

Execution không được bypass:

```text
Policy
  ↓
Permission
  ↓
Execution
```

Mọi execution path phải đi qua policy boundary trước khi side effect xảy ra.

Architecture test cần kiểm tra cả:

* import dependency;
* service wiring;
* execution call path;
* adapter bypass.

---

### 3.7. Orchestrator boundary

Orchestrator là Control Plane nhưng không được trở thành God Object.

Các responsibility phải nằm ở module chuyên biệt:

```text
Orchestrator
├── Decision Pipeline
├── Task Planner
├── Agent Selector
├── Capability Router
├── Permission Broker
├── Failure Recovery
├── Goal Manager
├── Task Queue
└── System Knowledge
```

Architecture test phải cảnh báo/FAIL khi Orchestrator trực tiếp sở hữu implementation của:

* Tool execution.
* Memory storage.
* Model provider.
* Sandbox.
* Scheduler internals.
* Persistence internals.

Orchestrator chỉ điều phối qua contract/service interface.

## 4. Invariants cần enforce

TASK-016 phải kiểm tra tối thiểu nhóm invariant `INV-001..INV-010` của M0–M4.

Các invariant được kiểm tra theo architecture boundary đã xác lập:

| Invariant | Nội dung cần enforce                               |
| --------- | -------------------------------------------------- |
| INV-001   | Orchestrator không trở thành God Object            |
| INV-002   | Agent không truy cập Tool trực tiếp                |
| INV-003   | Workflow không phụ thuộc implementation của Engine |
| INV-004   | Execution không bypass Policy                      |
| INV-005   | Capability là boundary giữa Agent và Tool          |
| INV-006   | Runtime Service chỉ truy cập qua contract          |
| INV-007   | Dependency phải theo layer direction               |
| INV-008   | Không tạo circular dependency                      |
| INV-009   | LLM không bypass deterministic control path        |
| INV-010   | Plugin/Skill không bypass Core/Runtime boundary    |

Các ID trên phải được đối chiếu với canonical architecture/invariant definitions trong repo trước khi implementation; TASK-016 không được tự thay đổi semantics của invariant.

Master Plan quy định architecture invariants là architecture-level gate; vi phạm phải làm architecture review FAIL.

## 5. Architecture Rule Categories

### ARCH-A — Import Boundary

Kiểm tra Python import graph.

Ví dụ FAIL:

```text
aios/agents/coder.py
    → aios/tool/python_tool.py
```

Expected:

```text
aios/agents/coder.py
    → capability contract
```

---

### ARCH-B — Forbidden Dependency

Danh sách dependency bị cấm theo layer.

Ví dụ Agent không được import:

```text
subprocess
docker
requests
provider SDK
filesystem implementation
database implementation
```

trừ khi dependency đó nằm sau một contract được phép.

---

### ARCH-C — Reverse Dependency

Phát hiện dependency ngược:

```text
Tool → Agent
Runtime → Orchestrator implementation
Capability → Agent
Workflow Engine → Workflow domain
```

---

### ARCH-D — Circular Dependency

Xây dependency graph:

```text
A → B
B → C
C → A
```

→ `ARCHITECTURE GATE = FAIL`.

Không chỉ kiểm tra Python import trực tiếp mà phải phát hiện cycle trong module/package graph.

---

### ARCH-E — Contract Boundary

Component public chỉ giao tiếp qua contract.

Ví dụ không cho:

```text
Agent → concrete PythonTool
```

mà phải:

```text
Agent → CapabilityContract
```

---

### ARCH-F — Policy Bypass

Phát hiện execution path:

```text
Agent → Tool → execute
```

mà không có:

```text
Policy → Permission
```

trong execution boundary.

---

### ARCH-G — Deterministic Path

Kiểm tra Decision Pipeline:

```text
Normalizer
 → Rule Engine
 → Workflow Matcher
 → Planner LLM
```

LLM chỉ được gọi khi deterministic path trả về `INSUFFICIENT`.

Không chấp nhận:

```text
Request → LLM → decide everything
```

Decision Pipeline của AIOS được thiết kế offline-first và deterministic-first.

---

### ARCH-H — Plugin Isolation

Skill/plugin không được import private Core implementation hoặc mutate Runtime internals.

Expected:

```text
Skill
 ↓
Public Skill Contract
 ↓
Capability / Runtime API
```

## 6. AST Scanner

Xây AST scanner cho Python source.

Scanner phải có khả năng:

1. Enumerate source files.
2. Parse AST.
3. Extract:

   * imports;
   * from-import;
   * function calls;
   * class inheritance;
   * decorators;
   * package/module ownership.
4. Xác định layer của module.
5. Áp dụng architecture rules.
6. Sinh violations.
7. Sinh machine-readable report.

Ví dụ:

```json
{
  "rule_id": "ARCH-002",
  "file": "aios/agents/coder.py",
  "dependency": "subprocess",
  "expected": "DENY",
  "severity": "ERROR",
  "status": "FAIL"
}
```

---

## 7. Architecture Graph

Scanner phải tạo dependency graph:

```text
Module A
   │
   ▼
Module B
   │
   ▼
Module C
```

Graph phải hỗ trợ:

* dependency traversal;
* reverse dependency;
* cycle detection;
* forbidden edge detection;
* layer violation detection.

Có thể dùng graph structure nội bộ đơn giản ở phiên bản đầu; không được kéo thêm dependency nặng nếu không cần thiết.

## 8. Violation Model

Mỗi violation phải có provenance.

Schema tối thiểu:

```text
ArchitectureViolation
├── violation_id
├── rule_id
├── invariant_id
├── file
├── line
├── source_component
├── target_component
├── violation_type
├── severity
├── message
├── evidence
├── detected_at
└── status
```

Severity:

```text
ERROR
WARNING
INFO
```

`ERROR` phải làm gate FAIL.

`WARNING` không được tự động nâng thành PASS nếu invariant yêu cầu hard gate.

---

## 9. Architecture Gate

Gate tổng:

```text
Architecture Scan
      ↓
Rule Evaluation
      ↓
Violation Collection
      ↓
Invariant Evaluation
      ↓
Architecture Gate
```

Kết quả:

```text
PASS
FAIL
UNKNOWN
```

Nguyên tắc fail-closed:

```text
UNKNOWN ≠ PASS
```

Nếu scanner không thể xác định một dependency quan trọng, phải trả `UNKNOWN` và yêu cầu review thay vì coi là hợp lệ.




```text

```

Fixture:

```text

```

```text

```

---

### 11.6. Deterministic routing test

## 14. Acceptance Criteria

### AC-001 — Layer enforcement

Dependency sai layer phải bị phát hiện.

```text
Expected: FAIL
```

### AC-002 — Agent/Tool boundary

Agent truy cập Tool implementation trực tiếp phải bị block.

### AC-003 — Capability boundary

Agent chỉ được truy cập Tool thông qua Capability contract.

### AC-004 — Workflow independence

Workflow domain không phụ thuộc trực tiếp vào engine implementation.

### AC-005 — Policy boundary

Execution bypass Policy/Permission phải FAIL.

### AC-006 — Circular dependency

Dependency cycle phải FAIL.

### AC-007 — Orchestrator boundary

Orchestrator không được sở hữu trực tiếp Tool/Provider/Storage implementation.

### AC-008 — Deterministic-first

LLM không được trở thành routing path mặc định.

### AC-009 — Plugin isolation

Skill/plugin không được bypass Core boundary.

### AC-010 — CI enforcement

Architecture violation làm CI FAIL.

### AC-011 — Fail closed

`UNKNOWN` không được tự động chuyển thành `PASS`.

### AC-012 — Regression

Architecture suite phải chạy cùng regression suite của các dependency trước đó.

### AC-013 — Evidence

Mỗi violation phải có file/line/rule/invariant/evidence đủ để developer truy nguyên.
