# M1 — Core Runtime

M1 là milestone xây **Runtime substrate** của AIOS. Mục tiêu không phải tạo một Agent hoàn chỉnh, mà tạo nền tảng để mọi execution về sau đi qua **contract → policy → permission → execution → state/evidence**, thay vì để Worker/Agent tự điều khiển hệ thống.

Canonical source định nghĩa M1 gồm **TASK-002 → TASK-009 và TASK-011**. 

---

## TASK-002 — Monorepo + `aios_core` Scaffold

### 1. Mục tiêu

Tạo skeleton Python/monorepo ổn định cho Runtime, đủ để các TASK tiếp theo có thể xây dựng service và contract mà **không phải thay đổi lại cấu trúc nền tảng**.

TASK này là nền móng kỹ thuật, vì các service của M1 phải có một namespace/package boundary rõ ràng ngay từ đầu.

### 2. Phạm vi

Bao gồm:

* Monorepo layout.
* Python package structure.
* `aios_core` runtime package.
* Configuration layer.
* Logging foundation.
* Package/project metadata.
* Runtime healthcheck.
* Test layout.
* CI/test bootstrap.

Không mở rộng sang:

* REST API.
* Worker/Agent.
* Plugin execution.
* Model routing.
* Orchestrator.
* UI.

Những thành phần này thuộc các milestone/TASK sau.

### 3. Kiến trúc cần hình thành

Skeleton phải tạo được boundary rõ ràng giữa:

```text
AIOS Repository
│
├── backend/
│   └── src/
│       └── aios_core/
│           ├── ...
│           └── ...
│
├── tests/
├── configs/
├── docs/
└── CI configuration
```

`aios_core` là runtime foundation; các layer phía trên phải phụ thuộc vào nó thông qua contract, không tạo một runtime song song.

### 4. Configuration

Configuration cần có một abstraction ổn định để các TASK sau có thể lấy:

* runtime configuration;
* environment-specific settings;
* service configuration;
* test configuration.

Không để từng service tự đọc environment variable hoặc config file theo cách riêng.

Mục đích là tránh tình trạng:

```text
Service A → os.environ
Service B → yaml riêng
Service C → dotenv riêng
Service D → hard-coded
```

mà phải hướng tới:

```text
Configuration
      ↓
Runtime Services
```

### 5. Logging

Logging foundation phải đủ để các service sau ghi nhận:

* service/component;
* lifecycle event;
* execution context;
* error;
* warning;
* diagnostic information.

Không biến logging thành audit system. **Audit/Event Service ở TASK-004** mới chịu trách nhiệm về event/audit semantics.

### 6. Healthcheck

Healthcheck phải có API/primitive ổn định để kiểm tra runtime foundation đã sẵn sàng.

Ít nhất phải phân biệt được:

```text
healthy
unhealthy
not-ready / unavailable
```

Không được coi việc process Python khởi động thành đồng nghĩa với Runtime đã ready.

### 7. Test foundation

Test structure phải cho phép TASK sau bổ sung:

* unit tests;
* contract tests;
* integration tests;
* architecture tests;
* regression tests.

Test bootstrap phải chạy được ngay cả khi chưa có các service M1 khác.

### 8. Deliverables

Canonical source yêu cầu:

> Repository skeleton + CI/test bootstrap. 

Bản triển khai chi tiết cần tạo tối thiểu:

* repository/package skeleton;
* `aios_core` package;
* configuration foundation;
* logging foundation;
* healthcheck;
* test structure;
* CI/test command;
* package metadata;
* basic documentation cho developer tiếp theo.

### 9. Acceptance Criteria

TASK được coi là đạt khi:

1. `aios_core` import được từ môi trường test.
2. Package installation/bootstrap chạy sạch.
3. Test runner khởi động được.
4. CI có thể chạy test suite.
5. Configuration có một entry point thống nhất.
6. Logging foundation có thể được khởi tạo mà không cần service implementation phía sau.
7. Healthcheck có thể được gọi độc lập.
8. Test layout đủ để TASK-003 trở đi bổ sung test mà không phá cấu trúc.
9. Không có dependency không cần thiết vào Agent/Worker/LLM/Provider.
10. Repository layout phù hợp quy ước M1.

Canonical acceptance criterion của source là **import/package/test bootstrap chạy sạch và layout phù hợp quy ước M1**. 

### 10. Test strategy

Test tối thiểu:

```text
test_package_import
test_configuration_bootstrap
test_logging_bootstrap
test_healthcheck
test_test_runner_bootstrap
```

Ngoài functional test, phải kiểm tra package boundary để tránh import ngược từ layer chưa tồn tại.

### 11. Definition of Done

TASK-002 chỉ đóng khi:

```text
Repository
   ↓
Package bootstrap PASS
   ↓
Test bootstrap PASS
   ↓
CI PASS
   ↓
Healthcheck PASS
   ↓
Architecture boundary PASS
   ↓
TASK-002 DONE
```

Không coi việc “folder đã tạo xong” là hoàn thành.

# TASK-003 — Kernel Foundations

### 1. Mục tiêu

Xây các primitive nền tảng để Runtime có thể quản lý dependency, contract và event một cách thống nhất:

* semantic versioning;
* contracts;
* dependency injection;
* event bus;
* execution-plan primitives.

Canonical source xác định chính xác phạm vi này. 

### 2. Vì sao TASK này cần tồn tại

Các service của Runtime không được tự kết nối với nhau bằng implementation cụ thể.

Ví dụ không nên:

```text
ExecutionService
    ↓
new PermissionService()
```

mà phải:

```text
ExecutionService
    ↓
PermissionService Contract
    ↓
DI Container
    ↓
Concrete implementation
```

Điều này cho phép:

* thay implementation;
* mock trong test;
* kiểm soát lifecycle;
* tránh coupling;
* kiểm tra architecture boundary.

### 3. Contract system

Contract phải hỗ trợ:

* schema/version;
* compatibility;
* validation;
* version mismatch detection.

Mục tiêu không chỉ là tạo Python interface.

Một contract cần trả lời được:

```text
Contract là gì?
Version nào?
Input schema nào?
Output schema nào?
Version hiện tại có tương thích không?
```

Canonical acceptance criterion yêu cầu **contract compatibility được kiểm tra**. 

### 4. Semantic versioning

Version phải có semantics ổn định để Runtime phân biệt:

```text
major
minor
patch
```

và xác định compatibility thay vì so sánh string đơn thuần.

Ví dụ:

```text
1.2.0 → 1.2.1
```

không nên được xử lý giống:

```text
1.2.0 → 2.0.0
```

### 5. DI Container

DI phải hỗ trợ ba lifecycle được canonical source yêu cầu:

```text
Singleton
Scoped
Transient
```

Ý nghĩa:

* **Singleton**: một instance trong lifecycle của container/runtime.
* **Scoped**: một instance trong execution/request scope.
* **Transient**: instance mới khi resolve.

Container phải hỗ trợ:

```text
register()
resolve()
scope()
```

và cho phép test thay implementation bằng mock.

Canonical acceptance criterion yêu cầu **service có thể inject mock**. 

### 6. Event Bus

Event Bus là primitive để các service publish/subscribe mà không coupling trực tiếp.

Cần phân biệt:

```text
Command
Event
Service call
```

Event Bus không được trở thành execution engine.

Ví dụ:

```text
ExecutionService
    → publish ExecutionStarted
```

không có nghĩa Event Bus tự quyết định workflow tiếp theo.

### 7. Execution-plan primitives

TASK này chỉ tạo primitive contract cho execution plan.

Không triển khai Planning Engine hoàn chỉnh ở đây.

Mục tiêu là tạo vocabulary chung cho các TASK sau:

```text
Plan
Step
Dependency
Input
Output
Status
```

Planning Engine thực sự thuộc M5/TASK-026 theo canonical roadmap. 

### 8. Deliverables

Canonical source yêu cầu:

* Core contracts.
* Container.
* Event primitives. 

Chi tiết triển khai:

```text
contract/
versioning/
di/
events/
execution/
tests/
```

### 9. Acceptance Criteria

PASS khi:

* Contract schema validation hoạt động.
* Contract version compatibility được kiểm tra.
* Incompatible version bị reject.
* DI singleton hoạt động đúng lifecycle.
* DI scoped hoạt động đúng scope.
* DI transient tạo instance mới.
* Service có thể inject mock.
* Event publish hoạt động.
* Subscriber nhận event.
* Event không tạo dependency trực tiếp ngược vào publisher.
* Execution-plan primitive có schema/validation cơ bản.

### 10. Definition of Done

```text
Contract PASS
      +
Version compatibility PASS
      +
DI lifecycle PASS
      +
Mock injection PASS
      +
Event publish/subscribe PASS
      +
Execution primitives PASS
      ↓
TASK-003 DONE
```

## TASK-004 — Runtime Services I

TASK-004 bắt đầu chuyển các primitive của TASK-003 thành **Runtime services thực sự**.

Canonical source xác định 5 nhóm chính:

* Context;
* Event/Audit;
* Artifact;
* Permission;
* Policy. 

### 1. Context Service

Runtime phải hỗ trợ **6 context types** theo canonical specification.

Context không chỉ là dictionary truyền quanh hệ thống. Nó phải có lifecycle và identity đủ để service biết execution hiện tại thuộc context nào.

Context phải có khả năng liên kết với:

```text
request
session
execution
workflow
agent/worker
artifact/evidence
```

nhưng không được tự ý mở rộng thành global mutable state.

### 2. Event/Audit Service

Cần tách:

```text
Event
Audit
```

Event phục vụ runtime communication.

Audit phục vụ traceability/governance.

Audit record cần có metadata đủ để xác định:

* ai/what tạo event;
* thời điểm;
* context;
* action;
* result/status;
* liên kết evidence nếu có.

### 3. Artifact Service

Artifact phải được quản lý như một object có identity và metadata.

Canonical source yêu cầu:

> artifact checksum/version. 

Do đó artifact lifecycle phải có:

```text
create
identify
version
checksum
store/reference
retrieve
```

Checksum dùng để kiểm tra integrity, không chỉ làm metadata trang trí.

### 4. Permission Service

Permission phải hỗ trợ **permission scopes**.

Mọi execution có side effect cần có permission boundary.

Permission không được để Worker tự quyết định:

```text
"tôi có quyền nên tôi chạy"
```

mà Runtime phải có một điểm kiểm soát thống nhất.

### 5. Policy Service

Policy là một trong các control points quan trọng nhất của Runtime.

Canonical source yêu cầu:

> policy pre-check. 

Do đó flow phải là:

```text
Request
   ↓
Permission / Policy Check
   ↓
ALLOW / DENY
   ↓
Execution
```

Không được:

```text
Execution
   ↓
Policy check
```

đối với policy pre-check.

Canonical acceptance criterion nói rõ:

> **Policy quyết định trước Execution**. 

### 6. Deliverables

* Context service.
* Event/Audit service.
* Artifact service.
* Permission service.
* Policy service.
* Interfaces/contracts.
* Tests.

### 7. Acceptance Criteria

PASS khi:

1. Mỗi service có contract rõ.
2. Service dependency được resolve qua DI.
3. Context không trở thành global mutable state.
4. Audit record có provenance/context.
5. Artifact có identity.
6. Artifact có checksum.
7. Artifact có version metadata.
8. Permission scope được kiểm tra.
9. Policy pre-check được thực hiện trước execution.
10. Không có service nào bypass contract.

### 8. Definition of Done

```text
Context
  +
Event/Audit
  +
Artifact
  +
Permission
  +
Policy
  ↓
Contract tests PASS
  ↓
Integration tests PASS
  ↓
Policy-before-execution PASS
  ↓
TASK-004 DONE
```
