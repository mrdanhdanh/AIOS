# TASK-014 — Tool + Capability Layer

## 1. Mục tiêu

Xây dựng lớp **Tool + Capability** làm cầu nối chính thức giữa Worker Plane và các công cụ thực thi bên dưới.

TASK-014 phải bảo đảm:

```text
Agent / Worker
      ↓
Capability
      ↓
Capability Router
      ↓
Tool Registry
      ↓
Tool Adapter
      ↓
Python / Docker / REST / MCP / Shell / Git
```

Worker không được biết hoặc chọn trực tiếp implementation của Tool.

Capability là abstraction mà Agent được phép nhìn thấy; Tool là implementation cụ thể phía dưới.

Mục tiêu cuối cùng:

* Tool được chuẩn hóa bằng contract.
* Tool tự khai báo capability.
* Capability Registry có thể discovery động.
* Một capability có thể có nhiều Tool implementation.
* Router chọn Tool phù hợp dựa trên health, priority và policy.
* Policy/Permission được kiểm tra trước khi Tool execution.
* Tool có thể thay thế mà không cần sửa Agent/Worker.
* Hệ thống vẫn hoạt động offline khi sử dụng Tool local/Mock phù hợp.

## 2. Vị trí trong kiến trúc

TASK-014 nằm tại boundary:

```text
                    CONTROL PLANE
                 AIOS Orchestrator
                         │
                         ▼
                  Capability Router
                         │
                  ┌──────┴──────┐
                  ▼             ▼
             Capability A   Capability B
                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
       Tool A   Tool B   Tool C
          │       │        │
       Python   Docker    MCP
```

Capability không thực thi công việc trực tiếp.

Tool không được trở thành control plane.

Agent không được bypass Capability để gọi Tool.

Luồng bắt buộc:

```text
Agent
 → Capability
 → Capability Router
 → Policy / Permission pre-check
 → Tool selection
 → Tool execution
 → Result
 → Evidence / Event
```

Nguyên tắc kiến trúc chung của AIOS yêu cầu Worker chỉ truy cập hệ thống thông qua Capability + Runtime, không truy cập Tool trực tiếp.

## 3. Phạm vi

### 3.1 Tool Contract

Định nghĩa contract thống nhất cho mọi Tool.

Tool metadata tối thiểu:

```yaml
tool:
  id:
  name:
  version:
  type:
  description:
  capabilities:
  permissions:
  resources:
  health:
  priority:
  enabled:
```

Tool Contract phải version hóa và tương thích với contract infrastructure của M1.

Tool type:

```text
python
docker
rest
mcp
shell
git
```

Không hard-code Agent với bất kỳ Tool type nào.

---

### 3.2 Tool Registry

Registry là nguồn discovery của Tool.

Registry phải hỗ trợ:

* register Tool;
* unregister Tool;
* lookup theo ID;
* lookup theo capability;
* enable/disable;
* đọc metadata;
* đọc health;
* đọc priority;
* kiểm tra version;
* kiểm tra compatibility.

Ví dụ:

```text
execute_code
 ├── python.local
 ├── python.sandbox
 └── docker.python
```

Một Capability có thể ánh xạ nhiều Tool.

---

### 3.3 Capability Declaration

Tool phải tự khai báo capability mà nó cung cấp.

Ví dụ:

```yaml
capabilities:
  - execute_code
  - run_python
  - run_tests
```

Runtime/Registry sử dụng declaration này để xây mapping:

```text
Capability → Tools
```

Không duy trì mapping thủ công riêng cho từng Agent.

Nguồn master plan xác định dynamic discovery: Tool khai báo `capabilities`, Runtime scan registry và tự map Capability ↔ Tool; một Capability có thể map nhiều Tool.

---

### 3.4 Capability Registry

Capability Registry quản lý abstraction mà Worker được phép sử dụng.

Ví dụ:

```text
Capability:
    execute_code

Providers:
    python.local
    python.sandbox
    docker.python
```

Capability Registry không chứa implementation execution.

Nó chỉ quản lý:

* capability identity;
* version;
* description;
* required permissions;
* required resources;
* provider Tools;
* health;
* availability.

## 4. Capability Router

Router nhận yêu cầu:

```text
CapabilityRequest
```

và trả về:

```text
CapabilityResolution
```

Ví dụ:

```text
Request:
    capability = execute_code
    constraints:
        language = python
        sandbox = required

Router:
    python.local       → rejected
    python.sandbox    → eligible
    docker.python     → eligible

Result:
    python.sandbox
```

Router phải **chọn Capability trước, Tool sau**.

Không để Agent tự quyết định:

```text
Agent → python.sandbox
```

Mà phải:

```text
Agent
 → execute_code
 → Capability Router
 → python.sandbox
```

## 5. Tool Selection Policy

Khi nhiều Tool cùng cung cấp một Capability, Router đánh giá tối thiểu:

### 5.1 Health

Tool unhealthy hoặc unavailable không được chọn.

```text
Tool A = unhealthy → reject
Tool B = healthy   → eligible
```

### 5.2 Priority

Nếu nhiều Tool đều hợp lệ:

```text
Tool A priority = 100
Tool B priority = 50

→ A preferred
```

Priority không được override Policy.

### 5.3 Policy

Policy phải được kiểm tra trước execution.

Ví dụ:

```text
Capability:
    execute_shell

Tool:
    shell.local

Policy:
    shell = DENY

→ Tool không được execute
```

Không được có logic:

```text
Router → Tool → Policy
```

mà phải:

```text
Request
 → Capability Resolution
 → Policy Pre-check
 → Tool Selection
 → Execution
```

Policy là một phần của control boundary, không phải trách nhiệm riêng của Tool.

## 6. Sáu Tool Adapter

### 6.1 Python Tool

Cung cấp các capability như:

```text
run_python
execute_code
run_tests
```

Không mặc định cấp quyền filesystem/network rộng.

---

### 6.2 Docker Tool

Dùng để thực thi workload trong container/sandbox boundary.

Có thể cung cấp:

```text

run_python

```

Sandbox Pool hoàn chỉnh thuộc TASK-015; TASK-014 chỉ phải tạo boundary cần thiết để Tool có thể được route đúng.

---

### 6.3 REST Tool

Chuẩn hóa HTTP/API invocation.

Ví dụ capability:

```text
http_request
call_api
```

Tool phải khai báo network requirement để Policy có thể đánh giá.

---

### 6.4 MCP Tool

Adapter cho MCP-based tools.

MCP server/tool implementation không được trở thành dependency trực tiếp của Agent.

Agent chỉ thấy Capability.

---

### 6.5 Shell Tool

Cung cấp:

```text
execute_shell
run_command
```

Đây là Tool có rủi ro cao nên permission/policy pre-check phải được enforce trước execution.

---

### 6.6 Git Tool

Cung cấp capability như:

```text
git_read
git_diff
git_status
git_commit
```

Quyền read/write phải được phân biệt qua Permission/Policy.

## 7. Tool Health

Mỗi Tool cần có health state tối thiểu:

```text
UNKNOWN
HEALTHY
DEGRADED
UNHEALTHY
DISABLED
```

Router phải xử lý:

```text
HEALTHY       → eligible
DEGRADED      → eligible nếu policy cho phép
UNHEALTHY     → reject
DISABLED      → reject
UNKNOWN       → không tự động coi là HEALTHY
```

Đặc biệt:

> `UNKNOWN` không được nâng thành `PASS` hoặc healthy chỉ vì Tool tồn tại trong Registry.

Điều này phù hợp nguyên tắc Evidence-First và fail-closed của master specification.

## 8. Capability Resolution Contract

Định nghĩa các thành phần logic:

```text
CapabilityRequest
CapabilityCandidate
ToolCandidate
CapabilityResolution
ResolutionReason
```

Ví dụ:

```yaml
request:
  capability: run_tests
  constraints:
    language: python
    network: deny

resolution:
  capability: run_tests
  selected_tool: python.sandbox
  status: RESOLVED
  reason:
    health: healthy
    priority: 90
    policy: allow
```

Nếu không tìm được Tool hợp lệ:

```text
UNRESOLVED
```

Không tự động fallback sang Tool vi phạm policy.

## 9. Permission / Policy Boundary

TASK-014 không tạo Policy Engine mới.

Nó phải sử dụng Policy/Permission Service đã có từ M1.

Boundary:

```text
Capability Request
       ↓
Required Permissions
       ↓
Policy Service
       ↓
ALLOW / DENY / ASK
```

### ALLOW

Tiếp tục Tool resolution/execution.

### DENY

Dừng execution và trả lý do.

### ASK

Chuyển qua Permission Broker để yêu cầu approval.

Không Tool nào được tự bỏ qua quyết định này.

## 10. Result Contract

Tool execution phải trả result chuẩn hóa, không trả implementation-specific object trực tiếp cho Agent.

Ví dụ:

```yaml
result:
  status: success
  tool_id:
  capability:
  output:
  metadata:
  duration:
  resource_usage:
  evidence_ref:
```

Failure:

```yaml
result:
  status: failed
  error:
  retryable:
  tool_id:
  capability:
  evidence_ref:
```

Kết quả phải có đủ metadata để Event/Audit/Evidence layer có thể truy vết.

## 11. Failure Handling

Các trường hợp tối thiểu:

```text
Tool not found
Tool disabled
Tool unhealthy
Capability unavailable
Policy denied
Permission denied
Tool timeout
Tool execution failure
Invalid Tool contract
```

Router không được tự động retry execution có side effect.

Retry/fallback phải phối hợp với Failure Recovery và Runtime Execution semantics.

Ví dụ:

```text
execute_code
   ↓
Tool A timeout
   ↓
Recovery policy
   ↓
Tool B eligible?
   ↓
Policy check
   ↓
Tool B
```

Không được:

```text
Tool A timeout
   ↓
bypass policy
   ↓
Tool B
```

## 15. Acceptance Criteria

### AC-001 — Tool Contract

Mọi Tool đăng ký phải conform Tool Contract và có metadata/version hợp lệ.

### AC-002 — Capability Declaration

Tool có thể khai báo một hoặc nhiều Capability.

### AC-003 — Dynamic Discovery

Registry có thể xây mapping:

```text
Capability → Tool[]
```

mà không cần hard-code Agent → Tool.

### AC-004 — Multi-Tool Capability

Một Capability phải có khả năng map tới nhiều Tool implementation.

### AC-005 — Health-aware Routing

Router không chọn Tool `UNHEALTHY` hoặc `DISABLED`.

### AC-006 — Priority-aware Routing

Khi nhiều Tool đều eligible, Router sử dụng priority để lựa chọn.

### AC-007 — Policy-aware Routing

Tool không được execution nếu Policy/Permission không cho phép.

### AC-008 — Fail-Closed

Không resolve Capability thành Tool khi:

* capability không tồn tại;
* Tool không hợp lệ;
* health không đủ;
* policy deny;
* permission deny.

### AC-009 — Worker Isolation

Worker/Agent không import hoặc invoke Tool implementation trực tiếp.

### AC-010 — Offline

Router + Registry + adapters có thể test hoàn toàn bằng mock/local Tool, không cần Internet.

### AC-011 — Evidence

Tool resolution và execution phải tạo metadata/evidence reference đủ để truy vết kết quả.

### AC-012 — Regression

Toàn bộ regression của M0/M1 phải PASS trước khi TASK-014 được DONE.

```text

  ↓
Capability
  ↓
Capability Router
  ↓
Policy / Permission
  ↓

```

Không được xuất hiện:

```text
Worker → Tool

Worker → docker SDK
Worker → MCP implementation

```

Tool cũng không được:

```text

Tool → bypass Policy
Tool → bypass Permission
```

Capability Router không được trở thành God Object.
