### 1. Mục tiêu

Xây **Graph Scheduler** để điều phối các node trong `ExecutionGraph` theo dependency, cho phép các node độc lập chạy song song nhưng vẫn tuân thủ:

* Dependency của DAG.
* Policy/Permission.
* Resource Service.
* Execution Service.
* State Service.
* Failure/Retry semantics.
* Không biến Scheduler thành Resource Manager hoặc Execution Engine.

Kiến trúc M5 yêu cầu tách rõ:

```text
Planning
   ↓
Execution Graph
   ↓
Graph Scheduler       ← TASK-028
   ↓
Resource Service      ← "Có thể chạy không?"
   ↓
Execution Service     ← "Thực thi thế nào?"
   ↓
State Service         ← "Đang ở trạng thái nào?"
```

Điểm quan trọng: **Graph Scheduler quyết định task nào READY và có thể dispatch; không trực tiếp sở hữu resource hoặc execution implementation.**

# 2. Phạm vi

### 2.1 Graph readiness

Scheduler phải đọc `ExecutionGraph` và xác định:

```text
PENDING
  ↓ dependency satisfied
READY
  ↓ resource + policy available
RUNNING
  ↓
SUCCEEDED / FAILED / ...
```

Ví dụ:

```text
        A
      /   \
     B     C
      \   /
        D
```

Scheduler phải đảm bảo:

```text
A → B
A → C

B và C có thể chạy parallel

B + C → D

D chỉ READY khi B và C hoàn tất theo JoinPolicy
```

---

### 2.2 Dependency-aware dispatch

Không được dispatch node khi dependency chưa thỏa điều kiện.

Ví dụ:

```text
A = RUNNING
B depends_on A
```

thì:

```text
B = PENDING
```

không được chuyển thành `RUNNING`.

Khi:

```text
A = SUCCEEDED
```

thì Scheduler reevaluate:

```text
B → READY
```

---

### 2.3 Parallel dispatch

Scheduler phải hỗ trợ nhiều READY nodes:

```text
READY:
  ├── test_backend
  ├── test_frontend
  └── lint
```

Nếu Resource Service cho phép:

```text
test_backend  ─┐
test_frontend ─┼─→ RUNNING
lint           ─┘
```

Nếu resource không đủ:

```text
READY
  ↓
ResourceService
  ↓
QUEUE
```

Scheduler **không tự cấp phát resource**.

# 3. Resource boundary

Đây là boundary quan trọng nhất của TASK-028.

### Graph Scheduler chịu trách nhiệm

* Dependency resolution.
* Readiness.
* Dispatch order.
* Parallelism.
* Join condition.
* Scheduling decision.
* State transition orchestration.

### Resource Service chịu trách nhiệm

* CPU.
* RAM.
* GPU.
* Token budget.
* Concurrent execution.
* Sandbox/container capacity.
* Grant / Queue / Reject.

Do đó không được tạo:

```python
scheduler.allocate_gpu(...)
scheduler.reserve_memory(...)
scheduler.execute(...)
```

Thay vào đó:

```text
Graph Scheduler
      ↓
Resource Service.request(...)
      ↓
GRANTED / QUEUED / REJECTED
```

Điều này trực tiếp phục vụ **INV-016 — Scheduler Separation**.

# 4. Policy boundary

Scheduler cũng **không được bypass Policy**.

Flow:

```text
READY
 ↓
Policy pre-check
 ↓
Resource check
 ↓
Dispatch
 ↓
Execution Service
```

Nếu policy:

```text
DENY
```

thì node không được chạy.

Nếu:

```text
ASK
```

thì node phải chờ approval theo policy contract.

Scheduler chỉ điều phối kết quả policy, không tự quyết định thay Policy Service.


Ví dụ:

# 7. Failure semantics

Scheduler không tự xử lý business retry.

Khi node fail:

```text
Execution Service
      ↓
FAILED
      ↓
Failure Policy
      ↓
Retry / Fallback / Block downstream
```

Scheduler nhận state mới rồi tính lại graph.

Ví dụ:

```text
A
├── B
└── C
```

Nếu B fail:

```text
B = FAILED
C = RUNNING
```

Scheduler không được tự kết luận D có thể chạy.

Nếu:

```text
D depends_on B + C
```

thì D phải:

```text
BLOCKED
```

trừ khi `FailurePolicy` của graph cho phép degraded execution.

---

# 8. Join Policy

Đối với node có nhiều dependency, Scheduler phải hỗ trợ JoinPolicy từ Execution Graph.

Ví dụ:

```text
D depends_on B, C
```

Có thể có:

```text
ALL_SUCCESS
ANY_SUCCESS
ALL_COMPLETED
```

Nhưng Scheduler chỉ **enforce contract đã được định nghĩa**, không tự thêm policy semantics ngoài contract.

Ví dụ:

```text
B = SUCCEEDED
C = RUNNING
D JoinPolicy = ALL_SUCCESS

D = PENDING
```

Khi:

```text
C = SUCCEEDED
```

thì:

```text
D = READY
```

---

# 9. Priority và fairness

Scheduler có thể hỗ trợ:

```text
priority
deadline
queue_time
```

nhưng không được phá dependency.

Ví dụ:

```text
A priority=low
B priority=high
B depends_on A
```

B vẫn **không được chạy trước A**.

Priority chỉ có hiệu lực giữa các node đã READY.

---

# 10. Backpressure

Nếu graph sinh ra quá nhiều parallel nodes:

```text
A
├── B
├── C
├── D
├── E
├── F
├── G
└── H
```

Scheduler không được dispatch toàn bộ mù quáng.

Flow:

```text
READY nodes
    ↓
Scheduler
    ↓
Resource Service
    ↓
capacity
    ↓
dispatch subset
```

Ví dụ:

```text
8 READY
Resource capacity = 3

RUNNING = 3
WAITING = 5
```

Khi một execution hoàn tất:

```text
resource released
      ↓
Scheduler reevaluate
      ↓
dispatch next READY node
```

---

# 11. Event-driven scheduling

Không nên polling toàn graph liên tục.

Scheduler nên phản ứng với các event chính:

```text
NodeSucceeded
NodeFailed
NodeCancelled
ResourceGranted
ResourceReleased
PolicyApproved
PolicyDenied
ExecutionResumed
```

Ví dụ:

```text
NodeSucceeded(B)
       ↓
Scheduler
       ↓
Recompute dependents
       ↓
D becomes READY?
       ↓
Resource check
       ↓
Dispatch
```

Điều này phù hợp với kiến trúc **Event-driven Runtime** đã có từ M1.

---

# 12. Cancellation

Nếu Execution bị cancel:

```text
Execution CANCELLED
```

Scheduler phải ngừng dispatch các node chưa chạy.

Các node:

```text
PENDING / READY
```

có thể chuyển:

```text
CANCELLED
```

Node đang `RUNNING` phải được gửi cancellation thông qua Execution Service.

Scheduler **không kill process/container trực tiếp**.

---

# 13. Resume

TASK-028 phải tương thích với snapshot/resume của Runtime.

Sau crash:

```text
Snapshot
   ↓
Restore Execution Graph
   ↓
Restore node states
   ↓
Scheduler rebuild READY set
   ↓
Resume
```

Không được chạy lại node đã:

```text
SUCCEEDED
```

trừ khi execution policy explicitly yêu cầu retry/replay.

---

# 14. Deterministic scheduling

M5 giữ nguyên nguyên tắc:

> Deterministic First → LLM Last.

Scheduler **không dùng LLM** để quyết định:

* dependency;
* readiness;
* resource dispatch;
* parallelism;
* state transition.

Các quyết định này phải deterministic và test được.

# 15. Architecture Invariant — INV-016

TASK-028 là nơi enforce rõ nhất:

**INV-016 — Scheduler Separation**

> Scheduler không sở hữu Resource hoặc Execution implementation.

Các architecture test cần bắt được những kiểu bypass như:

```text
GraphScheduler → subprocess
GraphScheduler → Docker
GraphScheduler → ResourceManager implementation
GraphScheduler → ExecutionService internals
```

Scheduler chỉ phụ thuộc contract/interface.

# 16. Test Strategy

### Unit

Test:

```text
A → B → C
```

Expected:

```text
A RUN
B WAIT
C WAIT

A SUCCESS
B READY

B SUCCESS
C READY
```

### Parallel

```text
A
├── B
└── C
```

Expected:

```text
A SUCCESS
B READY
C READY

B RUNNING
C RUNNING
```

Không bắt buộc B phải hoàn thành trước C.

### Join

```text
A → B
A → C
B,C → D
```

Verify:

```text
B SUCCESS
C RUNNING
D NOT READY
```

Sau:

```text
C SUCCESS
```

thì:

```text
D READY
```

### Resource saturation

```text
10 READY nodes
capacity = 2
```

Expected:

```text
2 RUNNING
8 WAITING
```

### Policy denial

```text
READY → Policy DENY
```

Expected:

```text
REJECTED/BLOCKED
```

và **không có Execution dispatch**.

### Failure propagation

```text
A → B → C
B FAILED
```

Expected:

```text
C BLOCKED
```

nếu failure policy không cho phép continuation.

### Resume

Snapshot:

```text
A SUCCESS
B SUCCESS
C RUNNING
D PENDING
```

Restart → restore → Scheduler tiếp tục từ state hiện tại.
