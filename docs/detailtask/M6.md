M6 gồm **6 task: TASK-029 → TASK-034**. Theo roadmap sạch, chưa task nào được mặc định là đã hoàn thành. 

Thứ tự chuẩn:

1. **TASK-029 — Harness Kernel + Contract + Registry + Run**
2. **TASK-030 — Execution Verification + Evidence + Replay**
3. **TASK-031 — Test Harness + Scenario + Simulation**
4. **TASK-032 — Evaluation Harness + Metrics**
5. **TASK-033 — Benchmark + Regression Gate**
6. **TASK-034 — Doctor + Readiness**

Roadmap đặt `TASK-029 → TASK-030`, sau đó **TASK-031 và TASK-032 có thể chạy song song**, rồi `TASK-033 → TASK-034`. 

Vì các task trong file Master Task Specification hiện đang ở dạng chuẩn hóa khá ngắn (`Objective → Scope → Deliverables → Acceptance → Dependencies`), phần chi tiết dưới đây nên bám **master plan gốc** để không tự bịa thêm scope. 

### TASK-029 — Harness Kernel

Mục tiêu: tạo nền tảng chung cho toàn bộ M6, với các contract:

`Harness → Context → Run → Event → Result → Artifact → Report`

Các thành phần chính:

* `aios/harness/contracts/`

  * Harness
  * Run
  * Result
  * Assertion
  * Report
* `aios/harness/kernel/`

  * Runner
  * Registry
  * Lifecycle
  * Context
* Lifecycle:
  `CREATED → PREPARING → VALIDATING → RUNNING → VERIFYING → COMPLETED`

  * lỗi: `RUNNING → FAILED → DIAGNOSED`
* `HarnessRun` phải có `run_id`, harness, target, version, environment, timestamps, status.
* Mọi run phải truy ngược được chuỗi:
  `Release → Harness Run → Execution Trace → Evaluation → Failure`.

**Gate:** Harness phải độc lập với implementation bên trong Runtime; chỉ sử dụng contract/API. 

### TASK-030 — Execution Verification

Đây là task quan trọng nhất của M6.

Nguyên tắc:

> Execution thành công không đồng nghĩa task thành công.

Verification phải kiểm tra:

`Preconditions → Execution → Postconditions → Invariants → Evidence`

Pipeline:

`Execution → Collect Evidence → Deterministic Checks → Policy Checks → Tests → Evaluation → Verdict`

Verdict:

* `PASS`
* `PASS_WITH_WARNING`
* `FAIL`
* `INCONCLUSIVE`

Evidence Package tối thiểu:

`request → normalized request → plan → execution graph → events → tool/test results → evaluation → artifacts → verdict`

Đặc biệt phải hỗ trợ **Replay**:

`Production Run → Trace → Replay → Simulation → Debug`

Không được suy luận `PASS` chỉ vì execution không phát sinh exception. Đây chính là **INV-019 — Verification Before Verdict**. 

### TASK-031 — Test Harness + Simulation

Mục tiêu: kiểm thử AIOS mà **không tạo side effect thật**.

Harness điều phối các loại test:

`Unit · Contract · Architecture · Integration · Workflow · Agent · Capability · Tool · Policy · Permission · E2E · Regression`

Nhưng không thay thế pytest/vitest.

Simulation:

`Request → Orchestrator → Planner → Execution Graph → Fake Runtime → Fake Tool → Expected Result`

Scenario được mô tả declaratively bằng YAML và có thể trở thành **Golden Scenario**.

Phải hỗ trợ Failure Injection như:

* model timeout
* tool failure
* resource exhausted

để kiểm tra Retry / Fallback / Recovery / Policy / Final State. 

### TASK-032 — Evaluation Harness

Khác với Test:

* **Test:** điều kiện có đúng không?
* **Evaluation:** chất lượng đạt mức nào?

Thứ tự evaluator:

`Deterministic → Semantic → LLM Judge → Human → Composite`

LLM Judge **không phải mặc định**.

Evaluation phải đánh giá cả:

* output
* trajectory
* correctness
* policy compliance
* tool accuracy
* cost
* latency

Quan trọng là **Trajectory Evaluation**: final output đúng nhưng trajectory có tool misuse / policy violation / retry bất thường vẫn phải được ghi nhận. 

### TASK-033 — Benchmark + Regression Gate

Mục tiêu: trả lời:

> "AIOS phiên bản mới có tốt hơn phiên bản cũ không?"

Benchmark phải theo dõi đồng thời:

`Quality · Cost · Latency · Tokens · Failure Rate · Policy Violations`

Ví dụ:

* Before: success `91%`
* After: success `86%`
* → **FAIL**

Hoặc:

* Quality `+2%`
* Cost `+80%`
* → `WARNING/FAIL` tùy policy.

TASK-033 biến Evaluation thành **release gate**, thay vì chỉ tạo báo cáo. 

### TASK-034 — Doctor + Readiness

TASK cuối M6 nâng cấp `aiagent doctor` và `aiagent arch-health` thành **AIOS Doctor Harness**.

Các domain:

`Architecture · Runtime · Workflow · Agent · Capability · Tool · Memory · Model · Policy · Registry · Performance · Security · Evidence`

Mỗi check chỉ được trả:

`PASS · WARNING · ERROR · UNKNOWN`

Readiness không được chỉ là một con số.

Ví dụ:

`Architecture 100% · Contracts 98% · Tests 97% · Evaluation 91% ...`

Quan trọng nhất là **hard gate**:

> `Policy violation > 0 → RELEASE BLOCKED`

ngay cả khi overall score rất cao.

Đây là bước đóng vòng M6: **Harness không chỉ test mà quyết định AIOS đã đủ điều kiện release hay chưa.**
