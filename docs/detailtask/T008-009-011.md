# M1 — Core Runtime

## TASK-008 — Workflow Definition + Compiler

### 1. Mục tiêu

Biến **Workflow** thành một first-class declarative contract của AIOS, hoàn toàn độc lập với workflow execution engine.

Mục tiêu cốt lõi là tách rõ:

```text
Workflow Definition
        ↓
      Compile
        ↓
Execution Engine
```

Workflow author không được biết hoặc phụ thuộc trực tiếp vào LangGraph hay bất kỳ engine cụ thể nào.

AIOS phải có khả năng:

* định nghĩa workflow bằng contract/YAML;
* validate workflow trước khi compile;
* compile cùng một workflow sang nhiều engine;
* chạy workflow ở chế độ simulation mà không tạo side effect thật;
* lưu workflow definition như artifact có version;
* thay thế LangGraph mà không phải sửa workflow contract.

Đây là nền tảng để M2 có Workflow Matcher + Workflow Library và để M5 nâng cấp workflow thành Execution Graph.

### 2. Phạm vi

#### 2.1 Workflow Definition Contract

Định nghĩa schema declarative tối thiểu:

```yaml
workflow:
  name: review_project
  version: "1.0.0"
  description: Review project source code

  nodes:
    - id: analyze
      type: task
      capability: analyze_code

    - id: test
      type: task
      capability: run_tests

    - id: report
      type: task
      capability: generate_report

  edges:
    - from: analyze
      to: test

    - from: test
      to: report

  retries: 2
  timeout: 300

  resources:
    cpu: 2
    memory: 2GB

  permissions:
    - filesystem.read
    - process.execute
```

Contract phải hỗ trợ tối thiểu:

* `name`
* `version`
* `description`
* `nodes`
* `edges`
* `retries`
* `timeout`
* `resources`
* `permissions`

Các trường phải được validate trước khi workflow được đưa vào compiler.

#### 2.2 Node Contract

Mỗi node phải có identity và execution semantics rõ ràng.

Node có thể tham chiếu:

* task;
* capability;
* workflow step;
* deterministic operation.

Node không được chứa implementation phụ thuộc trực tiếp vào engine.

Ví dụ:

```yaml
- id: run_tests
  type: task
  capability: run_tests
```

Không được:

```yaml
engine: langgraph
langgraph_node: ...
```

trong public workflow contract.

#### 2.3 Edge Contract

Edge mô tả dependency giữa các node.

Ví dụ:

```text
analyze → test → report
```

Ở M1 chưa yêu cầu đầy đủ DAG scheduler của M5, nhưng contract phải không ngăn cản việc mở rộng thành DAG.

Compiler phải phát hiện tối thiểu:

* node không tồn tại;
* edge trỏ tới node không tồn tại;
* duplicate node ID;
* duplicate edge;
* invalid workflow structure;
* cycle nếu cycle không được workflow contract cho phép.

#### 2.4 Compiler Interface

Tạo abstraction:

```text
WorkflowDefinition
        ↓
WorkflowCompiler
        ↓
CompiledWorkflow
```

Compiler interface phải cho phép thêm engine mới mà không sửa Workflow Definition.

Tối thiểu có:

```text
LangGraphCompiler
MockCompiler
```

Architecture mục tiêu:

```text
              Workflow Contract
                     │
             Workflow Compiler
                /           \
               /             \
      LangGraph Compiler   Mock Compiler
             │                 │
        LangGraph          Simulation
```

#### 2.5 LangGraph Compiler

LangGraph chỉ là **một implementation của compiler**.

Compiler chịu trách nhiệm chuyển declarative workflow thành execution representation tương ứng của LangGraph.

Workflow layer không được import trực tiếp implementation nội bộ của LangGraph.

#### 2.6 Mock Compiler

Mock compiler phục vụ:

* unit test;
* integration test;
* simulation;
* offline development;
* architecture verification.

Mock compiler phải có deterministic behavior.

Ví dụ:

```text
Workflow
  ↓
Mock Compiler
  ↓
Fake Execution
  ↓
Expected Events / Result
```

Không cần LLM.

#### 2.7 Simulation

CLI phải hỗ trợ workflow simulation.

Ví dụ:

```bash
aiagent run workflow.yaml --simulate
```

Simulation phải:

* parse workflow;
* validate contract;
* compile bằng Mock Compiler;
* tạo execution representation;
* mô phỏng node execution;
* phát event;
* tạo execution result;
* không gọi external tool thật;
* không yêu cầu LLM;
* không tạo side effect ngoài artifact/evidence cần thiết.

Simulation là tiền đề cho Harness M6.

#### 2.8 Workflow Validation

Validation tối thiểu gồm:

```text
Schema
  ↓
Metadata
  ↓
Node references
  ↓
Edge references
  ↓
Dependency structure
  ↓
Permission declaration
  ↓
Resource declaration
  ↓
Compiler compatibility
```

Workflow invalid phải fail-closed.

Không được:

```text
invalid workflow → best effort compile → execute
```

Phải:

```text
invalid workflow → REJECT
```

# TASK-009 — Capability Foundation

## 1. Mục tiêu

Xây nền móng cho mô hình **Capability-First** của AIOS.

TASK-009 tạo bốn thành phần liên kết:

```text
Capability Registry
Prompt Registry
System Catalog
Knowledge Graph v1
```

Mục tiêu là để AIOS không cần hard-code:

```text
Agent → Tool
```

mà sử dụng:

```text
Agent
  ↓
Capability
  ↓
Registry / Router
  ↓
Tool
```

Capability là abstraction mà Worker Plane nhìn thấy.

Tool implementation có thể thay đổi mà Agent không cần thay đổi.

Ngoài Capability Registry, TASK-009 tạo metadata foundation để AIOS có thể:

* discover component;
* search component;
* biết relationship giữa Agent/Skill/Workflow/Capability/Tool;
* version prompt;
* xây System Knowledge ở M2/M4.

## 2. Phạm vi

### 2.1 Capability Contract

Capability phải là first-class metadata object.

Ví dụ:

```yaml
capability:
  id: execute_code
  version: "1.0.0"
  description: Execute code in controlled environment
  permissions:
    - process.execute
  resources:
    cpu: 2
    memory: 2GB
```

Capability không phải implementation của Tool.

Một capability có thể map nhiều tool:

```text
execute_code
   ├── PythonTool
   ├── DockerTool
   └── RemoteExecutionTool
```

### 2.2 Capability Registry

Registry phải hỗ trợ tối thiểu:

```text
register()
get()
list()
find()
remove()
resolve()
```

Registry phải lưu metadata:

* capability ID;
* version;
* description;
* required permissions;
* resource requirements;
* provider/tool mappings;
* health;
* availability;
* tags.

### 2.3 Dynamic Discovery

Theo Capability Discovery model của AIOS, Tool tự khai báo capability trong ToolContract:

```yaml
capabilities:
  - execute_code
  - run_python
  - run_tests
```

Runtime scan registry và tạo mapping:

```text
Capability ↔ Tool
```

Một capability có thể có nhiều implementation.

TASK-009 chỉ xây foundation cho discovery; Tool Layer hoàn chỉnh được tiếp tục ở M2/TASK-014.

### 2.4 Capability Isolation

Worker/Agent không được chọn tool trực tiếp.

Đúng:

```text
Agent
  ↓
Capability
  ↓
Capability Registry
```

Không được:

```text
Agent
  ↓
PythonTool
```

Đây là một phần quan trọng của Architecture Invariants.

### 2.5 Prompt Registry

Prompt trở thành first-class component.

Prompt metadata tối thiểu:

```text
prompt_id
version
template
variables
metadata
created_at
updated_at
```

M1 chỉ yêu cầu template engine đơn giản:

```text
str.format subset
```

với placeholder dạng:

```text
{identifier}
```

Không đưa Jinja2 vào M1; theo roadmap, Jinja2 thuộc giai đoạn sau.

Prompt phải có version.

Ví dụ:

```text
code_review
  v1.0.0
  v1.1.0
```

Prompt Registry phải hỗ trợ:

```text
register
get
version lookup
list
```

### 2.6 System Catalog

System Catalog là "mục lục" của AIOS.

Nó không phải registry mới thay thế các registry hiện hữu.

Mục tiêu:

```text
Registry data
     ↓
System Catalog
     ↓
Index
     ↓
Search
```

Catalog index metadata từ:

* Agent Registry;
* Skill Registry;
* Workflow Registry;
* Capability Registry;
* Tool Registry;
* Prompt Registry;
* Model Registry;
* Artifact metadata.

Orchestrator sau này không cần scan toàn bộ registry mỗi request.

### 2.7 Catalog Search

Tối thiểu hỗ trợ:

```text
search(query)
find_by_id(id)
find_by_type(type)
find_by_tag(tag)
```

Ví dụ:

```text
search("execute_code")
```

có thể trả:

```text
Capability: execute_code
Tools: PythonTool, DockerTool
Agents: Coder
Workflows: code_execution
```

M1 chỉ cần metadata/index foundation; System Knowledge query intelligence hoàn thiện ở M2.

### 2.8 Knowledge Graph v1

Knowledge Graph biểu diễn relationship giữa metadata objects.

Node types tối thiểu:

```text
Agent
Skill
Workflow
Capability
Tool
Artifact
Model
Prompt
```

Edge ví dụ:

```text
Agent --USES--> Capability
Capability --IMPLEMENTED_BY--> Tool
Skill --PROVIDES--> Capability
Workflow --REQUIRES--> Capability
Agent --USES--> Prompt
Workflow --PRODUCES--> Artifact
```

### 2.9 Knowledge Graph Storage — M1 Boundary

Theo amendment của roadmap:

> M1 graph v1 sử dụng **in-memory storage** và populate **thủ công qua API**. SQLite persistence và automatic build từ registry/event bus để M2/M4. 

Do đó TASK-009 **không được mở rộng scope** thành:

* graph database production;
* automatic event-driven graph builder;
* SQLite persistence;
* distributed graph;
* graph reasoning engine.

Mục tiêu M1 chỉ là chứng minh graph contract và traversal cơ bản.

### 2.10 Graph API

Tối thiểu:

```text
add_node()
get_node()
add_edge()
get_edges()
neighbors()
find_path()
```

Ví dụ:

```text
capability = execute_code

neighbors(capability)
→ PythonTool
→ DockerTool
```

Graph phải giữ metadata của node/edge và version.

### 2.11 Graph Consistency

Graph phải reject:

* node không có ID;
* duplicate node;
* edge tới node không tồn tại;
* invalid node type;
* invalid edge type.

Graph query không được tự tạo relationship nếu evidence/metadata không tồn tại.

RuntimeKernel có thể compose và resolve các M1 services qua DI.

### AC-011-08 — Offline

M1 core test suite có thể chạy mà không yêu cầu external LLM.

### AC-011-09 — Evidence

### AC-011-10 — Fail Closed

Một architecture/policy/regression failure phải làm M1 gate:


không được chuyển thành PASS bằng cách bỏ qua test.
