# ADR-0008 — AIOS 1.x Behavioral Conformance

- **Status:** ACCEPTED
- **Date:** 2026-08-22
- **Supersedes:** —
- **Superseded by:** —
- **Related tasks:** T089 (Behavioral Conformance), T090 (Harness Coverage +
  Readiness), T091 (Meta-Harness / Verify-the-Verifier), T092 (System Readiness

- **Related ADR:** ADR-Compatibility (M12), ADR-ARCH-1.0 (Architecture 1.0 Freeze)

## 1. Context

AIOS 1.0 shipped with a frozen public contract surface (T064) and a compatibility
policy (ADR-Compatibility, M12). That policy proves a build is *structurally*
compatible (api / schema / event / version / contract). But it does not prove the
system *behaves* correctly: two builds can be structurally compatible yet diverge
in observable behavior.

M13 answers:

* How do we specify **observable behavior** (not just contracts)?
* How do we know the **harness actually covers** the system surface?
* How do we know the **harness itself is correct** (verify-the-verifier)?
* When is a build **certified** on the strength of behavior, not just structure?

Without behavioral conformance, a "compatible" build could silently regress in
observed behavior — violating the trust/evidence guarantees of the platform.

## 2. Decision

We adopt a four-layer behavioral/harness chain for AIOS 1.x:

1. **Behavioral Conformance (T089).** Behavior is specified as observable
   `given`/`when`/`then` scenarios. A deviation from `then`, or a non-observable
   spec, fails conformance (fail-closed). Every run carries provenance (T001).
2. **Harness Coverage + Readiness (T090).** The harness surface is mapped to
   coverage; a build is `READY` only at/above the coverage threshold (default:
   full coverage). Gaps are always reported. Only `READY` reports certify (T073).
3. **Meta-Harness (T091).** The harness is verified by known-answer and mutation
   tests, with the verifier locked per run (T078). Wrong known-answer, undetected
   mutation, or unlocked verifier → meta `FAIL` (fail-closed).
4. **Readiness vs Trust (T092).** A build is certified only when the system is
   `READY` **AND** the harness is `TRUSTED` (coverage `READY` + meta `PASS`).
   Either condition missing → no certification (fail-closed).

All four layers are **fail-closed, provenanced, and deterministic**: the same
input always yields the same verdict, and an unverifiable / untrusted state never
promotes to PASS / CERTIFIED.

## 3. Rationale

* **Observable-only specs** keep conformance objective — we never assert internal
  state we cannot observe, which avoids false confidence.
* **Coverage gating** prevents "green but untested" builds from being certified.
* **Verify-the-verifier** closes the loop: a harness that lies about behavior
  cannot silently pass.
* **Both-required certification** (ready AND trusted) matches the trust model —
  a healthy system with an untrustworthy harness must not be certified, and vice
  versa.
* **Determinism + provenance** make every behavioral decision auditable and
  reproducible, consistent with T001 Rule 5 and ADR-Compatibility.

## 4. Consequences

* `aios/behavioral` drives + observes behavior and emits fail-closed conformance.
* `aios/harness_coverage` maps surfaces → harness and gates readiness.
* `aios/meta_harness` runs known-answer + mutation tests with T078 verifier lock.
* `aios/readiness_trust` combines system readiness with harness trust into a
  single certification gate (T073).
* `aios/behavioral_docs` reviews the behavioral spec + this ADR for coverage,
  rationale, and staleness (T071 DX).
* No runtime feature is added; M13 is purely behavioral/harness governance.
